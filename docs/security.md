# Security component proofs

Current clusters use [peer administration with service-ordered encrypted configuration](peer-authority.md): every unrestricted node has equal authority, and the latest committed cluster sequence wins. The proofs below also retain coverage of legacy owner-based authority and its migration.

## Protocol versions

Encrypted node records carry an explicit `version`. Version 2 uses `chat`,
`chat_id` and `node_id` in registrations, plus `sender_chat`, `sender_chat_id`
and `recipient_chat_id` in message records. The decoder maps each supported
version into the same internal model before checking authority and permissions.
Version 3 adds [Merkle directory reconciliation](discovery.md#directory-reconciliation)
with the same chat field names. Version 4 adds directory snapshots on ordinary
records and direct bounded repair pages between trusted enrolled replicas.
These snapshots include a persistent per-replica sequence and subtree hashes.
V3 probes cannot be encoded as v1/v2; V4 pushes and snapshots cannot be encoded
as earlier versions. Unknown versions and mixed field shapes are rejected. User text and file bytes
are never rewritten by a codec.

Nodes negotiate the highest mutually supported record version through encrypted
presence replies. A capability proof must match a fresh outstanding challenge
and the peer's enrolled signing key. Support is cached for 90 seconds; stale or
unknown support uses v1. Newest supported versions are advertised first, followed
by older proofs and the ordinary reply. Presence uses v1 until V4 support is
known, then also carries the directory snapshot. An authenticated V4 record
confirms the sender can use V4. Ordinary presence challenges still determine
reachability; directory repair never claims a chat can receive a turn.
`gent nodes --json` reports the selected `wire_version` for each peer.

Queued records retain the version and exact bytes chosen at admission. The v1,
v2, v3 and v4 decoders remain available across restarts and rolling upgrades. Existing
v1 activity-capable peers keep receiving v1 records. Upgrades need no new chat
identities or cluster enrollment.

Future format changes should add an explicit codec and capability version,
retain decoders for queued versions, and test mixed versions and restart recovery.
Signed configuration, cryptographic domain labels, backup schemas and message
retry fingerprints have separate compatibility requirements. A record-envelope
upgrade does not rewrite previously signed or hashed data. Retire an old decoder
only after its queued data has drained or an explicit migration has handled it.

`gent-crypto` verifies owner-approved node identities and signed configuration history. The live daemon uses that authority for RPC permission checks and owner configuration changes. `gent-daemon::encrypted` supplies MLS messaging and authenticated directional streams, including configuration recovery after authority expires. An optional background dispatcher synchronizes encrypted configuration through a development relay, updating the live database and its policy. Node pairing is available through private-file invitations or authenticated SSH. The same dispatcher carries encrypted chat registrations, messages, files, and recipient receipts between directly paired nodes.

[Node connectivity](node-presence.md) uses encrypted challenge/reply events on those streams. Only a timely reply to the persisted outstanding challenge refreshes reachability. This owner diagnostic grants no authority, exposes no chat inventory, and never wakes a host. The central relay still observes traffic timing and size. Older pre-release readers stall on the new event until upgraded; authenticated buffered records remain available for recovery.

[Chat renaming](providers.md#rename-a-chat) changes only the authenticated registration's label, or a local registration selected by its hosting node's owner. It requires current node authority, an active registration and the expected generation. Queueing the existing encrypted registration update shares the label/generation transaction. A stale retry cannot undo later changes. Renaming cannot grant permissions or replace the authenticated binding. The final valid registration generation is reserved for revocation.

## Trust boundary

The optional [user-controlled remote MCP gateway](gateway.md) terminates hosted tool calls directly on a trusted node. Host credentials authorize conversation namespaces; per-call host metadata selects a persistent chat credential. This requires a trusted host that prevents model control of that metadata. Direct TLS, registry/node pins, revocation checks and [owner-approved OAuth](gateway-oauth.md) are implemented; installed CLI login and Codex per-call thread metadata are verified; hosted-provider provenance and integration remain unverified. Gent's central relay continues receiving encrypted daemon traffic. The model provider and gateway node see tool plaintext. The gateway has no Gent-hosted plaintext bridge.

OAuth clients can use a shared secret or [pinned RS256 client assertions](gateway-oauth.md#register-a-client-that-signs-token-requests). Signed clients require exact external identity, audience and short lifetime checks, plus persistent single-use assertion IDs. They have no secret fallback. Public keys are imported by the owner; JWT headers cannot introduce keys or fetch URLs. Assertions authenticate token requests and do not replace user consent, PKCE or per-call conversation metadata. Owner-controlled key updates require the expected revision, persist before export repair and preserve chat bindings and token families. Removing a signing key prevents new assertions from that key; host revocation terminates existing grants.

Explicit owner commands can [import published metadata or refresh its keys](gateway-oauth.md#import-published-client-metadata). Fetching requires canonical public HTTPS URLs on port 443, exact client identity, same-origin JWKS, supported signed authentication and a published callback list containing the owner's selection. Gent retains only that selection. Each fetch accepts at most 32 DNS answers, rejects any private/reserved address and pins the validated results for TLS. Proxies, redirects, compressed responses and non-JSON bodies are rejected; each document has a 64 KiB limit and a ten-second fetch deadline. Other document URLs are ignored. The chosen publisher's HTTPS identity authorizes the imported public key material; this does not verify its per-conversation metadata or account ownership. Failed fetches/validation preserve current keys.

An explicit `gateway run --client-metadata CLIENT_UUID` enables [runtime CIMD](gateway-oauth.md#enable-cimd-for-selected-hosts) for that existing signed host and permits published keys to replace its pinned set. Unknown IDs cause no fetches. Before authorization/token exchange, a selected host must pass active registration and resource checks and have current metadata validation. Cache reuse is limited to one minute and shortened by HTTP freshness headers; key revisions invalidate it. Failed/cancelled refreshes cannot reuse stale validation. Fetch concurrency and per-host attempt limits bound outbound work. Keys commit through the existing revision/export transaction; callbacks and grants cannot expand. Restart clears cached validation. Existing access tokens retain their original expiry unless the host is revoked. Automatic namespace creation, idle refresh scheduling, and hosted-provider acceptance remain unfinished.

Optional [`--subject-key`](gateway.md#scope-conversations-to-a-host-user) adds a host-reported user to the chat binding. It requires OAuth and a user field distinct from the conversation field. Each grant pins its first valid user report; a changed user is rejected before selecting a chat, including after refresh and restart. A separately approved grant can recover the same user/conversation, while different users with equal conversation IDs receive different credentials. First-use pinning and credential allocation share the registry transaction. Missing metadata or capacity refusal does not consume the unbound state. Raw user/conversation values are hashed with separate protocol labels; they do not appear in status or logs. Hashes are not protection against guessing low-entropy identifiers from a stolen registry.

Registry version 6 and export version 5 retain the subject policy, with required per-client markers and explicit per-grant unbound/bound records. Lost policy or subject fields reject access; setup retries cannot remove the requirement or migrate old chats to another namespace. Existing unscoped clients keep their prior mapping. This protects separation only when the authenticated host reports user metadata faithfully and keeps it outside model control. It does not authenticate the reported provider account independently, protect against a compromised host, or establish a multi-user cluster feature. Actual hosted user metadata remains unverified.

Gateway grants may additionally pin a client CA and exact DNS SAN. TLS proves possession of the client key; request and tool boundaries recheck the grant's certificate policy and validity alongside token checks. Browser consent needs no client certificate. Stored requirements cannot be omitted on setup retries or satisfied by HTTP headers, and plaintext listeners cannot authenticate those grants. Leaf rotation under the same CA/name preserves chat bindings; automatic CA rotation and certificate revocation-list checking are not implemented. See [certificate setup and limits](gateway.md#require-a-client-certificate). This validates a synthetic TLS peer; hosted-provider certificate and conversation behavior remain unverified.

A trusted endpoint pins a cluster ID, owner verification key, and genesis-state digest. This `TrustAnchor` must arrive through an already trusted endpoint or a separately authenticated owner channel. Taking an anchor from the routing service would let that service substitute its own authority.

The owner signing key authorizes membership and policy. Each node has a separate signing key and stable node ID. The local MCP binding credential and owner RPC credential remain separate from both cryptographic identities. A provider label, GitHub login, database membership row, or model-supplied node ID cannot authorize a signed revision.

This version assumes one active configuration writer holding the cluster's owner key. Recovery copies must remain offline until the writer is deliberately replaced. Concurrent holders of that key can sign competing histories; receivers reject forks against their saved checkpoint, but this implementation does not provide distributed consensus between independent owner writers. Delegated nodes can submit configuration proposals to that writer. Owner-key replacement remains unfinished. [Delegated permission editing](administration.md) now permits exact-pair changes and separately enabled selector-rule edits under scoped grants; broader chat configuration remains unfinished.

[Owner recovery evidence](owner-recovery.md) authenticates surviving nodes' reports of accepted checkpoints under their pinned node keys. A private challenge and short collection deadline bind reports to one review. Expired authority may be reported without renewing it. Matching reports do not establish global freshness, stop the old writer or authorize signer replacement. Missing and conflicting reports remain explicit; no revision or timestamp selects a winner.

The [signer succession protocol](owner-succession.md) supports consecutive owner epochs under the original trust anchor, with signatures from the preceding and successor keys. Accepted history cannot return to a retired signer or replace an accepted epoch. Trusted daemon APIs activate a node-bound successor with a complete decision journal and confirmed replacement streams to all enrolled peers. New source authorizations require saved readiness evidence signed by both successor keys, including independently verified peer receipts and grant bindings. Local key references and adopted decisions commit with authority. Issued authorization and journal pages can travel through the encrypted configuration recovery route after lease expiry, with candidate, grant and journal verification inside the receive transaction. Delivery cannot activate an owner or authorize ordinary expired-lease traffic. Preparation orchestration remains unfinished; no owner-replacement command is available yet.

Signed states contain private node names, membership, and policy; signatures alone do not conceal them. The configuration dispatcher encrypts these records in established MLS streams before upload. Initial grants and key packages travel through the invitation's authenticated Noise channel or trusted SSH pairing and are never published to the relay in plaintext. A future hosted bridge must receive only its chat's scoped credentials and grants, never this full configuration or the owner key.

The [recovery boundary](recovery.md) refuses operational access to directories marked `recovery-required.json`, including nested profiles and aliases. It runs before profile selection, daemon startup, configuration mutation, database opening and local RPC. Encrypted offline backups include manifest origin authentication, full verification and guarded extraction. The separate [history exporter](recovery.md#export-offline-history) reads only an authenticated archived database through read-only SQLite and publishes historical records and verified file bytes without credentials, keys or live queues. It never calls runtime storage or activates saved encryption state. Archives preserve historical secrets and cannot establish current authority. Lost joined nodes can be replaced with fresh identities through SSH or scoped invitations; owner replacement remains unfinished. A copied database must not be started as the old node.

[History assignments](recovery.md#assign-history-to-a-current-chat) require the local owner credential and explicitly map one historical chat's sent/received messages to one current local chat. The CLI authenticates the archive and pins the temporary export manifest; the daemon verifies inventory hashes, private owned files and selected content inside one transaction. Separate local tables preserve original IDs and provenance without inserting live chats, messages, grants or transport jobs. Archived labels and expired messages are covered by this explicit historical read grant; they do not establish current membership, reply authority or new instructions. Every read checks the current chat and assignment. Owner removal deletes content and retains a revision receipt; explicit restoration checks that revision so stale retries cannot regrant access. Revoking the recipient also stops reads. There is no chat tool for assigning or restoring history.

Recovered content remains plaintext at the trusted endpoint and can reach the recipient's provider through normal MCP calls. It has no automatic cluster replication or new central service route. Limits are 256 receipts including retired ones, 8,192 messages, 256 MiB of record/file content and 2 MiB of provenance metadata; owner removal frees content but not receipt/metadata capacity. Migration of old identities and peer permissions, actual hosted-provider recovery acceptance, pending-work reconciliation and owner-key replacement remain separate recovery work.

[Fresh binding recovery](recovery.md#recover-a-conversation-binding) is an owner-only operation. Registration, its network announcement and selected history assignment share one daemon transaction. A private local journal is published before a new credential or scope file; pending journals block ordinary MCP use. Exact retries reuse that credential, including after a lost daemon reply. Completion removes the journal's secret and pins the returned chat/import IDs. Stable sidecar locks coordinate recovery and both explicit/host MCP binding paths, while the credential-file lock also excludes older clients. Guard checks cover original and resolved binding directories before writes. Conflicting destinations, changed scope, removed imports and revoked chats cannot be repaired by silently issuing a new identity. Current blanket and same-node policy applies to the fresh registration; old explicit permissions and live work are not restored. Local files and host configuration remain trusted endpoint state.

[Gateway recovery](recovery.md#recover-a-gateway-conversation) reserves an unused binding in an existing authenticated host namespace, including its optional host-reported user scope. Registry version 7 stores the credential and pending/completed receipt together, leaving ordinary bindings and host exports unchanged. Host calls, download authorization and recovery share the registry lock; pending lookups return before allocating a new credential or pinning an OAuth grant's user. Completion checks the same registry/node/client, credential and request fingerprint, and rejects changed result IDs or an inactive host. Daemon assignment and registry publication are separate transactions; exact retry finishes a lost reply. Host revocation during assignment can leave retained history with an unusable pending binding, which the local owner can remove explicitly. Recovery issues no OAuth consent, restores no old host authority and cannot establish metadata provenance for an unverified provider.

[Later backups](recovery.md#recover-an-import-from-a-later-backup) can re-export one explicitly selected historical import. Read-only validation checks its stable receipt ID, original participant scope, normalized records, file bindings, chunk/whole-file hashes, byte accounting and storage format before publishing anything. Removed receipts supply no content; missing/incomplete files remain unavailable. Revocation of an archived recipient is preserved in provenance and does not authorize any current chat. A new owner assignment is required to expose those records. Re-export retains the earlier archive and assignment chain, bounded at 64 entries, without activating old encryption state or restoring old grants. That lineage is historical data authenticated by the containing archive's recovery key; it does not independently prove each sender or current authority. Earlier snapshots can still contain subsequently removed data.

## Account sessions

The account-login prototype uses a dedicated GitHub OAuth app with no requested scopes. Browser login checks state and uses S256 PKCE with an ephemeral loopback callback; headless login uses device authorization. The account Worker verifies the token's app, scopes and stable GitHub subject before issuing service access. GitHub credentials remain transient; SQL stores no raw provider tokens. Local fixture proofs pass on both OSes, but real GitHub consent and production deployment remain unverified.

The CLI generates a timestamped 256-bit service bearer and saves it before exchange, allowing recovery if the response is lost. The service stores its SHA-256 digest and an initial 30-day expiry. Login retries retain that expiry; revoked credentials cannot reactivate. Admission limits and a short creation window prevent retired credentials from becoming fresh sessions after verifier cleanup. Logout of an absent candidate remains pending until that window closes; SQL checks its own clock during insertion and logout so an in-flight login cannot commit a new session after logout confirms expiry. Account suspension or deletion permanently revokes existing sessions even if the account later becomes active again.

Explicit `POST /v1/auth/session/renew` accepts the current Gent bearer and its observed `expected_expires_at`. SQL extends an active session only during its final seven days, to 30 days from the database clock. The expected expiry is a compare-and-set condition: stale or repeated requests return current authority without another extension. The same transaction extends still-active, authorized transport credentials under that session. Expired credentials and retired nodes, memberships or clusters do not renew. Database triggers reject identity changes, expiry rollback, overlong leases and revocation reversal. A transaction failure preserves both old account and transport expiries. Invitation deadlines remain fixed.

The daemon checks on startup and hourly, contacting only the pinned account service when its saved lease is near expiry. The login mutation lock serializes renewal with logout. Pending/disabled logins and changed account/service pins are refused. Renewal preserves the service and transport bearers and all encryption keys; a lost response is recovered by reading current authority. It authenticates the Gent session without contacting GitHub. Active use can keep a session alive indefinitely; this is renewable bearer access, with no token rotation or absolute session lifetime. Logout or account revocation terminates it. A session that actually expires requires fresh login and node reconnection.

Notification sockets pin the lease under which they connected. Renewal can close an old socket, and the existing reconnect loop uses the same credential with the extended lease. Ciphertext history remains available. Account-fixture and relay tests cross synthetic near-term deadlines; they do not replace the planned multi-week operational trial.

Local credentials live in `~/.gent/auth/session.json`, separate from cluster configuration and keys, beneath private directories with private file permissions and a mutation lock. Status validates the current session remotely; cached identity never proves current authentication. Logout first marks the credential locally disabled. If the service is unreachable, server revocation remains pending and the disabled credential is retained solely for retry. Successful logout clears the record. Other software running as the same OS user remains trusted.

Account SQL contains identity links, session digests, opaque cluster IDs and service memberships. Each operation uses a fresh primary D1 session; mutations recheck authority in their transaction. These records contain no messages, private cluster names, policies or encryption keys. Service membership cannot create a valid cryptographic enrollment or grant decryption access. The account API now authorizes the service-backed relay described below. The separate shared-token development relay remains independent of account logout and cluster retirement.

## Service-backed relay authority

The local service prototype issues a separate credential for each service node. Its `gent_t1` prefix distinguishes it from the account bearer, owner RPC key and chat binding. The daemon's relay reader accepts this format; owner/chat credential readers retain their original format. SSH development pairing does not copy service credentials. [First-owner setup](service-setup.md) persists local keys and signed genesis before reserving their real node/cluster IDs at the service. A private journal pins the account and endpoint, retains uncertain credential admissions, and serializes setup against the daemon and login/logout. Nodes enrolled through SSH or invitations provision independent credentials under their own account sessions. Their snapshots include only service/relay metadata, and preflight checks require the same account and service before enrollment. Local signed identity is checked before credential admission; cryptographic owner and joined roles remain distinct.

A cluster owner issues transport credentials under an active account session. The service stores their digests, node/cluster association and expiry. Credentials expire with the issuing account session. Logout revokes that session's dependent credentials; other sessions remain independent. Suspension, cluster retirement, membership revocation and node revocation also deny access. Revoked node IDs retain tombstones, including when revocation precedes first enrollment. Restoring an account or membership cannot reactivate revoked credentials.

The relay checks current account authority through a service binding for each HTTP request and before each notification. Digest checks require a separate service-to-service secret; a digest is not a public bearer. There is no cross-request authorization cache, and unavailable authority denies access. Uploads are checked again after buffering and waiting for a Durable Object's gate. Already admitted operations may complete after a concurrent revocation.

Mailbox keys, file storage, quotas, cleanup and notification realms are scoped by the authenticated cluster. Identical external resource IDs in different clusters remain isolated. Hibernating sockets retain only a credential digest and scope, never the bearer. Periodic alarms recheck idle connections and close revoked or expired access; the target interval is 30 seconds, subject to platform scheduling. Service mode limits connections to 64 per cluster and four per credential.

These credentials authorize cluster-level ciphertext transport for trusted daemons. They do not enforce private chat permissions, approve cryptographic node keys or convey file keys. Hosted chats and plaintext bridges must receive narrower endpoint capabilities. First-owner setup and service-backed SSH joining now bind service records to the actual signing node/cluster identities; their local proofs check those bindings and separate issuing sessions. Service revocation does not replace signed cryptographic node removal or retract delivered plaintext.

Local proofs cover identical-ID isolation, revocation, restarts, notifications and native encrypted transport on Linux and macOS. Guided setup and active-session renewal have separate native/Worker proofs. Production deployment, real GitHub consent, restore reconciliation and aggregate service budgets remain unfinished.

### Coordinated node removal

`gent node remove NODE_UUID` requires the local signing owner and rejects its own node ID and unknown members. The owner commits the signed membership removal, history publication and pending service intent together. Database version 16 retains the target cluster, node, signing key, original removal revision and account/service pin. The journal allows at most 8,192 records, consistent with the signed retired-node limit; exact retries remain available at capacity. An established database refuses to recreate a missing removal journal. Records remain local to the owner and contain no bearer or private signing key.

The CLI and daemon require the original setup, cluster, service and account pins before sending the idempotent service DELETE. The login lock serializes this request with login/logout and session renewal. Only a successful service response advances the local record to `confirmed`; response loss or a failed local write leaves a retryable intent. Service confirmation reports relay access revocation, without claiming peer convergence. The owner daemon scans pending work at startup and every 30 seconds, with a rotating cursor and at most 16 records per pass. A failed request cannot erase the signed removal or its retry record.

Existing streams and chat operations check current signed membership. Once a remaining peer applies the removal, it rejects the retired node's streams and treats its chats as revoked. Other peers retain their independent links. The removed node may never receive its own removal because its service access and configuration grant are no longer valid; offline peers can keep older authority until they synchronize or their signed lease expires. Previously delivered plaintext and admitted service operations cannot be retracted. Owner transfer, key-loss recovery, remote removal delegation and physical deletion of historical ciphertext remain separate work.

## Local cluster selection

Version-2 local TOML can hold a `[contexts]` registry with up to 128 distinct absolute profile directories, keyed by cluster UUID and pinned to a node UUID. The original cluster remains a profile at its existing directory. Selection never moves keys, databases, queues, bindings or authentication state. CLI resolution checks private ownership, the canonical directory and current cluster/node IDs. It resolves one level only; a selected profile cannot redirect the operation through its own default selection. Missing or replaced state does not cause fallback. This registry is owner-local metadata and is excluded from signed membership and encrypted configuration replication.

Local registry edits and ordinary configuration saves share a persistent `config.lock`. A save merges the latest registry under the lock before projecting signed policy. This prevents a stale daemon projection from overwriting a concurrent switch. Lock acquisition waits at most three seconds; failure leaves the saved selection unchanged. External editors do not participate in this lock and must preserve the local registry when editing TOML.

Installed daemon, MCP and Claude hook entry points use explicit physical directories and stay there across process restarts. Host binding mode requires an explicit directory or cluster selection. Fixed MCP binding files gain a private scope sidecar containing cluster/node IDs and a credential digest. Scope mismatch fails before registration. A preexisting unscoped binding requires its original explicit context once; new ephemeral connections select their default at launch. Sidecars are endpoint metadata, not enrollment evidence or credentials. Their deletion or restoration is subject to the same trusted-OS-user and backup limitations as other local state.

Additional-profile setup reserves a private directory and local-creation identities in `profile-setup.json` before provisioning. An empty journal is written before its UUID is pinned in the primary TOML; jobs are added only after that pin commits. Missing established journals and mismatched node IDs fail. Completed records remain for retries, bounded at 128 jobs; primary selection commits before the completion marker so a lost completion write can resume. Enrollment retains its existing owner/invitation/SSH journals and cryptographic checks. This local journal does not prevent coordinated rollback of a complete backup or tampering by the trusted OS user.

Managed profiles share account sessions by reference. Both `auth/account-source.json` and local TOML pin the canonical source directory, source node/cluster IDs, account and origin. Source references are flattened; chains and concurrent local/shared bearer stores are rejected. Account operations and daemon renewal use the source `session.lock`; logout affects every linked profile. Bearers are not copied into children. Account changes and origin redirection are checked before requests and again against authoritative session responses. These references grant no cluster signing authority. Node keys, transport credentials and databases remain independent. Configuration version 3 lists its required local fields in `local_features`. Missing or invalid registry, account-reference or setup-journal metadata fails validation instead of silently changing routing. Registry and metadata writes share `config.lock` and survive stale daemon projections.

## Keys and signed records

Owner and node keys use Ed25519 through `ed25519-dalek`, with system randomness and strict signature verification. Weak public keys are rejected. A node cannot use the owner key, share another active node's signing key, or reuse a retired key. Owner and node signing-key types have no `Debug` or serialization implementation. Explicit secret export returns a zeroizing buffer for protected endpoint storage.

Signed bodies use [RFC 8785 JSON canonicalization](https://www.rfc-editor.org/rfc/rfc8785.html) through `serde_jcs`. The signing inputs are:

```text
gent/cluster-state/v1<NUL> || JCS(ClusterState)
gent/enrollment-request/v1<NUL> || JCS(EnrollmentRequest)
gent/configuration-grant/v1<NUL> || JCS(ConfigurationGrant)
gent/legacy-chat-binding/v1<NUL> || JCS(LegacyAgentBinding)
```

The signature is Ed25519 over those bytes. State digests and enrollment fingerprints use SHA-256 over the corresponding signing input. Domain separation prevents a signature for one record type from authorizing another. Digests exclude the detached signature. Numeric counters and timestamps stay within JSON's exactly representable integer range.

Wire decoders require canonical JSON bytes, enforce size limits before parsing, reject unknown fields, and reject duplicate map entries through canonical re-encoding. A decoded record still needs signature and authority verification. The public signing/state types have explicit version fields; unsupported versions fail validation.

Current limits are:

| Record or collection | Limit |
| --- | --- |
| Signed configuration | 2 MiB |
| Enrollment request | 4 KiB |
| Configuration stream grant | 8 KiB |
| Active nodes | 1,024 |
| Retired node IDs / signing keys | 8,192 each |
| Policy rules / groups | 4,096 / 256 |
| Members per policy group | 4,096 |
| One history batch | 1,024 revisions and 16 MiB |

These are validation bounds for the prototype. History compaction and operational quotas remain future work.

## Node enrollment

1. The new node generates its own signing key and node ID locally.
2. It obtains the cluster's trusted anchor and current checkpoint through the pairing flow.
3. It signs an enrollment request containing that anchor, base revision/digest, its node ID and public key, display name, random request ID, and validity period.
4. The owner authenticates the complete request through the protected pairing channel or independently confirms its complete 32-byte fingerprint. Echoing the fingerprint shown by an untrusted relay is insufficient. The CLI uses authenticated SSH or the invitation's authenticated Noise channel.
5. The owner verifies proof of key possession, fingerprint, target cluster, exact current checkpoint, and expiry, then signs the next configuration revision.
6. The joining node obtains a verified checkpoint directly from the trusted owner endpoint, or verifies the owner's history against its independently pinned anchor. Once installed, its authority advances only through verified history.

Requests last 15 minutes. An intervening configuration revision makes an unaccepted request stale; retrying requires a request for the new checkpoint and owner authorization. A protected SSH retry for an already approved node/key returns current bootstrap state without enrolling another node or issuing another revision. A different key, retired node, or different authority is rejected.

SSH enrollment additionally supports explicit [joined-node replacement](recovery.md#replace-a-lost-joined-node). Its signed request includes the old node ID and public key, pinned from the trusted owner snapshot, and requires a distinct new ID/key. The owner commits retirement, new membership and the old-to-new retry mapping together in one SQLite transaction and one signed revision. Exact retries require the recorded old key and replacement ID/key and still require the replacement to be currently authorized. Later removal or key rotation cannot be reversed by retry. The active signing owner is excluded. Ordinary enrollment, rotation and unscoped invitations reject replacement requests.

[Replacement invitations](recovery.md#replace-through-a-private-invitation) carry the exact old ID/key in an optional signed `replaces` field, omitted from ordinary offers. The Noise claim must prove a distinct new ID/key. Every operation checks the live target before enrollment or the committed replacement mapping afterward; a competing offer cannot adopt that mapping. Offered configuration rights cannot exceed the old node's rights. The dispatcher requires the signed enrollment's replacement scope to equal the offer, including on continuations, and refuses ordinary enrollment through a replacement offer. Continuation creation reads the original mapping from the permanent removal journal; the joining journal refuses changing or dropping it. This scope travels in the private file and encrypted channel, not account registration. Revocation of the old service credential uses the same asynchronous removal journal as SSH.

Replacement preserves an existing configuration-administration grant without expanding it. It leaves policy rules unchanged and does not migrate old chat identities, bindings, history, sends or grants. New streams and local RPC credentials are generated. Database version 17 adds the replacement identity to the existing removal journal, retaining its admission limit and service cleanup path. Service cleanup is asynchronous, and peers enforce retirement when they obtain current signed authority. A local replacement record is pinned in TOML and checked against the local signing identity and signed retirement. Its publication uses the existing staged manifest; recovery archives remain guarded and unused by enrollment.

`gent cluster join CLUSTER_UUID --via user@owner-host --name laptop` implements this flow through the owner's existing SSH login and local RPC credential. It requires trusted SSH host keys, disables interactive authentication and SSH agent forwarding, bounds protocol frames, and invokes only a dedicated pairing protocol on the remote machine. Remote command paths are shell-quoted; target names cannot inject SSH options or commands. Owner-only pairing RPCs are separate from MCP chat operations. No enrollment secret or private signing key belongs in a model-visible tool argument.

The joining machine saves its own key, the authenticated owner pin, and request IDs in a private sibling staging directory. The owner approves enrollment, then signs a two-node configuration-stream grant using the joining node's fresh MLS key package. A joining runtime receives no owner signing secret. Interrupted retries preserve identity and reuse committed operations; a stale unconsumed grant gets a fresh package and stream. Once its runtime is installed, it verifies bounded history batches through its saved checkpoint before accepting a grant at that exact revision. After configuration and both directional data streams are ready, an immutable publication manifest governs verified copies into the final home. Existing login state and lock-file inodes stay in place; conflicting files are preserved and `config.toml` is published last. Partial publication resumes from the same staged bytes while the daemon lock excludes startup. Existing configuration-only nodes can rerun joining to add data streams without replacing their identity or chat credentials. Old unused streams and abandoned joins currently require future retention/revocation work; local temporary-file deletion does not promise forensic erasure.

The owner must have a configured relay before enrollment. Development pairing copies its shared synthetic relay credential over SSH into a separate private file. Service-backed pairing sends only account/relay metadata and provisions the joining node's own credential after checking its account and cryptographic identity. Neither mode exports the owner signing key or local RPC credential. SSH bootstrap trusts the SSH-authenticated endpoint's verified snapshot; invitation bootstrap pins the trust anchor from the independently transferred private file. Subsequent installed state cannot be replaced by a new snapshot. A replaced owner pin is rejected on resume. Real GitHub consent, owner-key replacement, and recovery from an old whole-endpoint backup remain separate work.

The [invitation component](invitation-enrollment.md) implements signed offers, channel-bound node claims and a bounded Noise transport in `gent-crypto`. The native owner persists a single node/key/name claim before releasing a response-capable channel. A persistent private lock serializes claims, operations and revocation across Store instances. The restricted dispatcher rechecks the signed offer, current membership and privileges, service binding and saved claim for every operation. It allows only the claimed node's bootstrap and never exposes general owner RPC. The daemon polls the service mailboxes, and the private-file CLI persists exact invocation IDs and inputs through staging, publication and the encrypted Finish receipt. Interrupted enrollment preserves the node key; replacement offers require explicit continuation with matching owner, service and privilege pins.

Database version 14 introduced invitation drafts, claims, operation input digests and completion/group bindings. Version 15 also records admitted handshake IDs transactionally, preventing reuse across owner restarts. Reservations precede cryptographic effects; exact retries recover committed enrollment, grants and links after a failed journal write. Continuation offers preserve the enrolled node's identity and privileges, and domain-separated request IDs preserve its original groups across offers. The journal admits at most 128 retained invitations, 64 authenticated attempts per invitation, 8,192 operations per invitation and 32,768 operations overall, with four requests each for configuration grants, data grants and stream acceptance. Existing retries remain possible at capacity. Fresh authorized snapshots/history are recomputed rather than cached.

An independently committed admission-clock watermark and bounded creation-ID window prevent ordinary clock rollback from reactivating an expired invitation. Revocation erases its private secret and operation rows; it cannot undo membership or keys already delivered. Completion retains the secret until expiry solely for the original successful Finish receipt, after proving the same node key in a new session. Expiry cleanup deletes remaining journal rows without guaranteeing forensic erasure. Restoring an old whole-endpoint backup is outside this protection. The staged-join tests use real encrypted operations but synthetic account provisioning, and do not establish service routing. Secret buffers and the DH primitive use zeroization, but Snow's internal cipher/handshake state does not provide comprehensive secret-memory erasure.

Invitation UUIDv7 IDs now bind their whole-second issue time, which the native signed-offer verifier checks. The account service derives a fixed 15-minute deadline from the same ID, preventing old IDs from being registered after expired verifier cleanup. It stores opaque routing metadata and credential digests, with immutable issuing-session, owner-node and expiry bindings. A separate joining bearer requires the routing secret and same-account authentication; only the designated owner's node bearer can access the other side. These capabilities cannot authorize a cryptographic membership or replace protected delivery of the invitation file.

The service-auth relay isolates each invitation in a Durable Object with fixed attempt, message and byte budgets. It rechecks account authority for every request and again after buffering writes and acquiring its FIFO storage gate. Directional sequence records permit only byte-identical retries. Chunks, descriptors and counters commit together; expiry alarms remove storage, while service revocation blocks access before physical cleanup. Local proofs cover these boundaries, including concurrent writers, failed transactions, delayed uploads, outages, restarts, expiry deletion and storage/log scans with a deliberate plaintext control. That storage proof uses a separate `test-storage` build and local AEAD payloads. Default deployment builds exclude the failure hook. Separate native-driver and CLI proofs run actual Noise enrollment through these routes, including independent node credentials and Finish recovery after owner restart. A physical Linux-Mac proof passes in both enrollment directions, including actual invitation expiry, explicit continuation with the original key and streams, encrypted files/relay turns, and both daemon restarts. SSH handles protected invitation transfer, fixture control and local Worker port forwarding; Gent enrollment uses the Noise mailboxes with SSH fallback denied. Production service behavior remains unverified.

## Revisions, expiry, and revocation

Every state contains a revision number and the digest of its immediate predecessor. Receivers verify the owner signature, cluster/authority binding, contiguous revision, predecessor digest, nondecreasing issue time, and retained retirement history. An update chain is validated completely before changing the in-memory checkpoint. A signed record with a valid signature can still be rejected for a rollback, gap, or conflicting predecessor.

States currently last at most 24 hours. `authorize_node` requires a currently valid state and an exact match between the node ID and approved public key. Its result authenticates a node; chat discovery, messaging, and relay delegation still need their separate permission checks. Caller-supplied time must come from the trusted endpoint clock, never a model or relay field.

An expired state may be loaded to recover or synchronize. `advance_history` and `Replica::apply_history` accept verified history in bounded batches even when the latest batch is still expired. Node authorization remains unavailable until a fresh revision is reached. `apply_chain` and `Replica::apply` additionally require a fresh final revision. An owner with the correct signing key can renew expired state.

Under a partition or malicious relay, another endpoint may keep using its previously issued state until that state's validity ends. This implementation therefore has a revocation delay bounded by the remaining validity period, assuming a trustworthy clock. Local clock rollback and restoration of an older entire endpoint backup require additional recovery safeguards. The hosted trial must choose an acceptable freshness interval; the owner daemon now schedules renewals and distributes them over configuration streams.

Node signing-key rotation keeps the node ID and permanently retires its previous key. Node removal retires both its ID and key. Retired entries cannot disappear from later revisions, and removed identities cannot reenroll under fresh signatures. Rejoining a removed endpoint currently requires a new logical node identity and key. Removing the last node is rejected. The MLS proof below implements separate encryption-epoch changes, but orchestrating signing-key rotation across all affected groups remains unfinished.

## Durable endpoint state

`Replica` stores one cluster per private endpoint directory in `authority.sqlite3`. The database is mode 0600 beneath a mode-0700 directory. Symlinks, shared files, and unknown future schema versions are rejected. The SQLite database uses rollback journaling and extra synchronous commits, with the [database allocation policy](#database-allocation-and-journals) below.

The trust anchor, checkpoint, current signed state, and accepted revision history are retained locally. A write starts an immediate transaction, compares the caller's expected checkpoint with the stored checkpoint, validates every revision, inserts history, and advances current state and checkpoint together. The new verified state is returned only after commit. Concurrent stale writers must reload and reconcile their proposed changes.

Restoration verifies the exact state digest and revision against the saved checkpoint. An older signed state cannot replace a newer checkpoint. The trusted local checkpoint is part of the security boundary; a relay cannot supply a replacement checkpoint. Restoring the entire database from an old backup is outside this protection and must be addressed by the recovery procedure.

The standalone replica database contains private configuration, but no node or owner private keys. OS-user access to endpoint files remains trusted. The live runtime uses the shared authority schema described below instead of running a second `Replica` checkpoint alongside its queues.

## Live daemon authority

The owner-only `Diagnose` RPC used by [`gent doctor`](diagnostics.md) verifies current signed state in a read-only transaction. It does not update the admission clock, retry configuration projection, wake synchronization or run maintenance. Chat tools cannot invoke it. Diagnostics use fixed messages and selected metadata instead of raw parser errors, credentials, policies, account names or message content. Offline inspection does not open or migrate the database. Optional online account verification sends the saved service credential to its validated origin without renewing or persisting it; relay observations come from existing daemon work and grant no authority.

The local runtime stores authority, accepted history, MLS tables, registrations, exchanges, and message queues in one private `state.sqlite3`. Each RPC starts an immediate transaction, verifies the saved state and local node identity, and uses that state's policy for discovery, send, reply, inbox, and acknowledgment. Chat requests require fresh authority. A previously opened daemon handle reloads authority for every request; it cannot keep using an earlier policy from memory. Registration activity and message/exchange writes commit together.

First startup creates separate owner and node Ed25519 keys and pins genesis in `identity.key`, a mode-0600 file under the private state directory. The original `owner.key` remains the distinct local RPC credential. The owner file's `GENTKEY1` header precedes the two private keys and bootstrap records; it has no model-facing accessor. Key buffers are zeroized on drop. This is protected local storage, without OS keychain encryption or forensic-erasure guarantees.

`Store::install_joined` installs an already enrolled node using its own signing key and independently verified authority. Its `GENTKEY2` file contains that node's private key, trust anchor, checkpoint, and signed state, with no owner signing secret. It creates a separate local RPC credential and atomically installs the initialized directory, refusing to overwrite an existing configuration. This remains a trusted Rust API; the staged SSH and invitation joins call it after authenticated enrollment. A relay or MCP chat cannot invoke it. Joined nodes can submit authorized configuration proposals. Signing revisions, enrolling nodes and issuing administrative grants require current owner authority; a later authenticated handoff can assign that role to an enrolled node.

Bootstrap preserves existing local node and cluster IDs, registrations, and messages. An interrupted bootstrap reuses the same saved keys and genesis. Missing keys for an initialized database, mismatched identities, symlink/shared key files, or an authority anchor that differs from the separate key-file pin fail closed. The database must also be a private regular file. Restoring the entire key file and database from an older backup remains outside rollback protection.

Owner configuration changes create a signed revision, persist history/checkpoint, and queue a TOML projection in one transaction. Accepted changes are ordered by signed revision: the newest change replaces the previous shared configuration. Later authorized edits can replace an earlier policy without a merge, including edits begun from an older view. Invalid revisions, stale replay, and forks still fail verification. The commit immediately wakes the configuration dispatcher, with history available to each stream's publication cursor. Authorized joined nodes route durable encrypted edit requests to the active owner writer.

After commit, Gent writes the newest signed settings to `config.toml` atomically, preserving unrelated local settings. The file's `applied_revision` records that projection. A filesystem failure leaves committed authority in force and a durable retry marker; the RPC reports `applied: true` with `config_saved: false`. Restart, subsequent successful RPCs, and maintenance retry the latest state, never a saved older projection. Editing TOML alone does not change active authority: `gent config apply` authorizes and signs the edit. `gent node name set` also goes through the daemon and requires it to be running.

The owner daemon checks renewal at startup and every 15 minutes, renewing when at most six hours remain in the 24-hour lease. `gent cluster renew` requests an immediate owner renewal. Chat requests do not renew authority themselves. Expired authority blocks them until a renewal commits; failed renewal storage leaves them blocked. Other nodes receive signed renewals through their configuration streams and never self-renew. [Owner activation](owner-succession.md#live-activation) dynamically selects the accepted candidate key; the original bootstrap key cannot regain signing rights after retirement.

`OrderedEndpoint::open_runtime` attaches trusted daemon code to this database. Receiving a complete configuration revision advances the same checkpoint used by live RPC permission checks and queues the same TOML projection. Runtime tests pass encrypted packets directly between peers, including a newer denial that blocks an already queued message. Separate dispatcher tests exercise network synchronization through a local relay.

### Permission explanations

`gent permission explain ACTOR_UUID PEER_UUID` requires local owner authentication and reports the current signed revision, freshness, policy gates and all matching rules in both directions. An expired snapshot remains inspectable by the owner and is labeled stale. The shared `gent_permission_check` MCP tool binds the actor to the authenticated conversation and requires current membership and peer enumeration. Hidden, unknown and revoked peers return the same unavailable error. Chats receive only that pair's gates and blockers; rule indices, selectors, group membership and cluster revision metadata remain private. A policy check grants no reply right, does not reserve permissions and does not establish delivery. See [permission explanations](permissions.md) for field semantics. Separate [administration grants](administration.md) authorize bounded exact-pair edits and, with an explicit `selector_rules` opt-in, persistent node/group/blanket rules. Selector scopes and previews disclose no matching identities or counts. Named chats require existing visibility; group names must appear in an active visible rule or membership grant, with a separate applicable rule-edit grant required for the mutation. Structural containment never infers group/node subsets from present membership. Authorized rules can affect hidden and future matches. Existing grants omit the false flag from signed bytes and retain pair-only authority. All scope and visibility checks use pre-edit policy, and the signing owner repeats them at acceptance. Grants are immutable and permanently retired on removal; revocation stops future edits without undoing accepted rules. Origin-node checks precede audit insertion. Chat results omit raw rejection details and global revisions; owner history retains the origin, acting chat, exact changes and outcome. Chat-specific storage admission preserves capacity for owner requests. Separate group-membership grants now name an existing target group, editable member selector, add/remove actions and expiry. Named members must already be visible. Member lists filter both discovery and editing scope and expose no hidden count. Every mutation uses pre-edit policy and is rechecked at owner acceptance; group and permission edits share the retry namespace, quotas and retired grant IDs. Membership changes affect every rule and existing administration scope referencing that group, including the editing chat’s own authority. This effect is part of the explicit membership delegation; these tools cannot issue new grants or create/delete groups. See [group membership](administration.md#group-membership).

## Configuration proposals from joined nodes

Signed membership carries an optional `can_configure` capability. Missing or false values retain the previous canonical encoding and grant no delegated administration. Enrollment requests cannot set it themselves. SSH pairing grants it for newly enrolled nodes; invitations grant it by default unless created with `--no-configure`. Retries preserve current rights, including revocation. Existing older nodes require an explicit `gent node admin grant NODE_UUID` on the owner. Rotation preserves the approved capability, and removed nodes cannot receive new grants. The owner's signing key remains authoritative independently of this delegated flag.

The local owner RPC accepts policy replacement, cluster/current-node names from TOML, current-node renaming, and renewal requests. MCP credentials cannot invoke it. A joined node checks its last verified capability and selects exactly one current writer from its owner-signed configuration-stream grants. It atomically stores the proposal and outbound event, then sends it over its encrypted data stream. Request IDs are canonical nonnil UUIDs. Identical retries return the saved result; a changed proposal under the same ID fails. Local intent can be retained while authority is expired, but publication requires fresh authority.

The active owner rechecks the origin's current signed capability before accepting a proposal. It serializes each accepted edit against its current revision, so later acceptance wins even when the source began with an older policy. The signed revision, history, TOML projection marker, recorded result, and outbound response commit together. Validation and revoked grants produce durable rejection results; storage failures roll back and preserve the incoming record for retry. The grant permits neither further delegation nor enrollment, and the owner signing key never leaves the owner node.

Results bind the original writer, request ID, and proposal fingerprint. An applied result must reference a checkpoint already verified in local signed history. A response ahead of local authority waits for configuration synchronization. Requests remain queued while the owner is unavailable and survive source restart. Rejected results stay final after a later regrant. The CLI exposes these states through `gent config requests` and `gent config request REQUEST_UUID`. Configuration proposals share ordered data streams with other node traffic; congestion or a stalled stream can delay acceptance. Configuration-edit and transport retries have the storage limits described below; aggregate disk quotas remain unfinished.

## Relay permissions and saved selection

Relay uses the same enumeration, send, and receive policy as ordinary messages. New clusters permit communication between all registered chats; no separate relay grant or configuration edit is needed. Explicit restrictions apply before encryption, on import, before delivery, and when reading responses or files.

Each local chat has at most one current attachment. Selection, replacement, and the retry record commit in the same RPC transaction. Stable request IDs return the original selection, including its detached state. Status rechecks permissions and omits target details after enumeration loss. Detach addresses an attachment owned by the authenticated intermediary. New selections have no expiry and remain selected across restarts until detached or replaced. There is a limit of 1,024 retained attachments per chat. Detached selections can retire seven days after creation once their turns are gone and the original request can no longer be admitted.

Relay messages carry authenticated attachment, root-turn, and operation fields inside the encrypted envelope. The receiver binds each response or cancellation to the accepted root, its participants, and its expiry. Ordinary replies cannot strip relay context. Each turn expires after 24 hours, independently of the selection. Empty relay metadata is omitted to preserve existing message encodings and retry fingerprints. Upgrade both nodes before sending grant-free relay turns; older receivers cannot interpret them.

Existing signed relay grants and retirement records remain readable and verifiable. Attachments and turns created by older daemons retain their original grant, expiry, and revocation checks so an upgrade cannot revive revoked work. Selecting the target with a new request ID creates a selection under ordinary permissions, independent of legacy grants. Legacy CLI grant commands are hidden compatibility commands; `gent relay` now shows saved selections. Grant limits, immutable records, and retirement validation remain unchanged for historical state.

Root messages, retry records, ordered target queues, cancellation requests, final outcomes, and outgoing network events commit transactionally. Only the target's earliest unfinished turn can receive a local response; acknowledgment alone never advances the queue. The queue combines inputs from every intermediary in local arrival order. Temporary permission blocks pause the head, avoiding overtaking when permissions return. Expiry and permanently revoked legacy grants retire the head. Generic messaging is a separate queue and carries no relay ordering guarantee.

Each target can send 16 responses per turn, with the final slot reserved for `complete` or `cancelled`. A turn accepts one cancellation request; exact retries reuse its original message. A cancellation crossing a final reply does not reopen the turn. Detach affects future sends only. Source status and paged history remain tied to the original attachment and target, with content hidden when authority is lost. A terminal outcome reports what the target chat asserted; it does not audit host execution or prove that cancellation stopped a process. After uncertain host execution, the caller must reconcile before repeating consequential work.

No text supplied by a chat becomes authenticated human intent. Messaging permission allows relay communication, without overriding target execution approvals. The attachment's security mode comes from registered node identities and describes only the implemented daemon transport. Existing freshness bounds still apply to revocation while disconnected. Relay turns retire with their whole exchange under the [message retention rules](#message-retention-and-replay-admission).

## MLS messaging proof

The native proof uses [MLS, RFC 9420](https://www.rfc-editor.org/rfc/rfc9420.html), through OpenMLS 0.9.2, RustCrypto 0.6, and OpenMLS SQLite storage 0.3. The ciphersuite is `MLS_128_DHKEMX25519_AES128GCM_SHA256_Ed25519`. Gent does not implement its own ratchet. The workspace uses rusqlite 0.37 to share the SQLite storage provider's native library version; the existing daemon and replica tests pass with that version on both OSes. No experimental MLS protocol features or secret-debug features are enabled by Gent.

`EncryptedEndpoint` takes a trusted node identity and a private directory. Initialization saves independently authenticated authority once. Each later operation restores that authority against its stored checkpoint and authorizes the local node. Updates must follow the signed chain; opening the database cannot replace its anchor or node key.

An MLS basic credential contains the protocol version, cluster UUID, and node UUID. Its Ed25519 signing key must exactly match fresh owner-approved membership. `NodeIdentity` implements the MLS signer interface without exporting another private-key copy. A valid MLS signature under an unapproved key cannot impersonate a node. Group creation also checks the expected identity of every key package. Joining requires an explicit local roster and verifies every member against both that roster and authority. Standalone proposals, external senders, public application/commit messages, and additions to existing groups are rejected in this proof.

Key packages allow an endpoint to join asynchronously. The joining endpoint commits consumption of its private package only after the Welcome and expected roster pass validation. A failed join rolls everything back. An exact Welcome retry is recognized after restart. Allocate a new package request ID for each invitation; retrying an allocation returns its original public bytes, even after its private material has been consumed. This does not make a package reusable for another group.

Current bounds are 16 members per group, 16 KiB per key package, 256 bytes per group ID, 1 MiB per decoded application payload, and 2 MiB per MLS wire message. The encrypted application envelope carries a version, UUID, and base64 payload. Payloads can contain arbitrary binary data. Chat records validate filenames and content sizes, enforce message permissions, and carry inline files. Their 256 KiB fragments fit the Worker's 1 MiB frame limit after encoding. Independent attachment objects and message-bound grants use the separate file transport described below.

### Persistence and retries

MLS secrets, the authority checkpoint, ciphertext outbox, plaintext endpoint inbox, and receipt hashes live in one private `mls.sqlite3` database. It uses rollback journaling, extra synchronous commits, and SQLite secure deletion, with the [database allocation policy](#database-allocation-and-journals) below. Owner and node signing secrets are not stored there. Its inbox and cryptographic state are plaintext within the trusted endpoint; this proof does not supply storage encryption or protection against a compromised OS user.

Each cryptographic operation starts an immediate transaction and loads fresh MLS state through the upstream SQLite provider on that transaction's connection. A send advances the ratchet and stores its ciphertext before commit. A receive advances the ratchet, stores the plaintext, and records its receipt before commit. Welcome processing and epoch commits use the same pattern. Results are returned only after commit. Failure drops the in-memory MLS object as well as rolling back storage, so the next attempt reloads the saved ratchet.

Request UUIDs bind to operation and input hashes. A send retry returns the exact committed ciphertext; conflicting reuse fails. Receipts suppress duplicate delivery, and MLS still rejects a consumed generation when Gent's receipt cache is removed in a test. Concurrent writers serialize through SQLite and reload state; they cannot independently advance from stale in-memory ratchets. Queue inspection is limited to trusted daemon code, in batches of at most 128 records. The runtime integration below adds permission checks at actual chat delivery and authenticated acknowledgment. Queue pruning and disk quotas remain unfinished.

### Ordering, removal, and forward secrecy

The prototype retains no past epochs or resumption PSKs. It allows up to 32 skipped application generations within an epoch, with a maximum forward distance of 128. Encryption padding uses 256-byte blocks. These are proof parameters, not final operational settings.

MLS must process earlier application messages before the commit advancing their epoch. The low-level tests demonstrate that an undelivered old-epoch message becomes undecryptable after that commit. The directional stream layer below enforces this order and buffers packets that arrive early, including commits. It no longer depends on a relay supplying the correct order. A missing packet stalls that stream until retransmission; the relay can always withhold traffic. Lost-state recovery must not grant it decryption authority.

Fresh owner authority is checked before application encryption and acceptance. An unapproved or removed credential in the group blocks new application sends. `remove_revoked` removes those credentials and commits a new epoch; surviving endpoints validate the resulting roster against their authority. A removed endpoint retaining its old authority and old keys cannot decrypt a new-epoch message. A signed revocation must reach a surviving endpoint before it can enforce it; the authority lease still bounds withholding as described above. Previously delivered plaintext and previously issued keys cannot be recalled.

The tests establish deletion of consumed key packages and loss of old-epoch decryption through the current logical MLS state. They do **not** establish forensic erasure from allocator memory, SQLite WAL history, filesystem snapshots, swap, or backups. `secure_delete` alone cannot provide that guarantee. Secret-storage design, backup exclusions, key retention, and recovery need review before claiming full endpoint-compromise forward secrecy in a deployed service.

## Directional encrypted streams

`gent-daemon::encrypted::ordered::OrderedEndpoint` supplies the delivery primitive used by the daemon. Each stream has one pinned sending node and an explicit recipient roster. A reply uses a separate stream in the opposite direction. Two peers can therefore send and refresh keys concurrently without competing to commit the same MLS group. Broadcast to several approved nodes uses the same single-writer rule. This is a transport role; it does not require a coordinator chat or constrain which chats may talk to each other.

The originating node creates an MLS group and publishes its Welcome as sequence zero. The receiving node independently approves the writer and roster, checks the outer packet signature, and verifies that the MLS Welcome was authored by that same writer. The stream saves the writer's node ID and approved signing key, origin digest, original-roster digest, and current sequence/digest locally. These identities and roster records do not appear in the outer packet.

Every packet signs this exact binary input with the node's Ed25519 key:

```text
gent/stream-packet/v1<NUL>
|| version:u8
|| group_id_length:u16be || group_id
|| sequence:u64be
|| previous_packet_digest:[32]
|| SHA256(mls_ciphertext):[32]
```

The packet digest is SHA-256 of that signing input, excluding the detached signature. Sequence zero has an all-zero predecessor; later positions require a nonzero predecessor. Counters are bounded to JSON-safe integers. Wire records use canonical JSON with base64 ciphertext, group ID, and signature, and reject duplicate/unknown fields or noncanonical encodings. Packet size is bounded to 3 MiB around a maximum 2 MiB MLS message. This signature authenticates ordering; MLS remains the encryption protocol.

Opaque group IDs, counters, predecessor hashes, ciphertext lengths, signatures, and timing remain visible to transport. Chat names, node IDs, public keys, request IDs, message bodies, and private configuration are absent from this outer framing. Key-package distribution still requires its encrypted channel.

### Durable ordering and backpressure

Sending, MLS epoch changes, signed packet insertion, and advancement of the stream checkpoint commit together. Repeating a request ID returns its original packet. Concurrent operations on one node reload state under SQLite's immediate transaction lock. Only the pinned writer may send or change that stream's epochs; the general MLS proof APIs reject mutations and receives on ordered groups so callers cannot accidentally bypass sequencing.

`stage` checks current authority and the writer's signature before saving a packet. It recognizes exact repeats and rejects conflicting accepted or buffered sequence slots. Packets may be at most 128 positions ahead of the saved head. Pending application ciphertext is limited to 16 MiB across the endpoint database. Future packets can occupy at most 13 MiB, reserving 3 MiB for a missing immediate predecessor. Once a ready prefix occupies that reserve, callers must drain it before staging more data. Configuration traffic has a separate quota, described below.

`drain` applies only the next sequence with the expected predecessor digest. Each packet gets a separate transaction covering MLS state, inbox/receipt insertion, stream checkpoint, accepted digest, and pending-row deletion. A later failure cannot undo an earlier committed prefix. Authority is rechecked when applying previously buffered data. The sender inside MLS must equal the pinned outer writer, including for epoch commits. Status exposes the next needed sequence, and the signed outbox supports bounded retransmission from that position.

Schema version 4 retains stream metadata, signed outbox records, recent accepted digests, and pending ciphertext. It includes stream purpose, authority history, configuration grants, publication cursors, partial records, and sequence metadata for wire receipts. Existing version-1, version-2, and version-3 databases upgrade without replacing their MLS state or queued ciphertext. Migrated authority history starts at the saved current checkpoint; it cannot reconstruct earlier revisions. A previously used unsequenced group cannot be adopted into an ordered stream. Ordered retries now reconstruct their original MLS bytes from the retained signed packet; redundant legacy copies are compacted in bounded batches. Authenticated receiver confirmation, outbound packet retirement, and total disk quotas remain unfinished.

### Revocation and conflicting history

An offline recipient can encounter older traffic before the commit removing another member. For directional backlog, the writer and local receiving node must still be authorized. Historical refreshes may preserve an existing credential or remove a now-revoked credential; they cannot add a member, replace a signing identity, or remove a currently authorized node. This lets the recipient reach the removal commit without reviving the revoked node or retaining old epochs indefinitely. Earlier ciphertext may already be known to the removed recipient; revocation cannot undo that exposure. New sends remain blocked until revoked members are removed, and final chat delivery still needs a current policy check.

A writer's revocation or signing-key replacement disables its existing streams. Applying that authority update also removes its pending ciphertext in the same transaction, freeing the receive quota while preserving other writers' queues. Revocation of the local endpoint clears its entire pending queue. Replacement stream enrollment and key-recovery UX remain to be implemented. A receiver cannot take over an offline writer's stream; it can continue sending through its own direction while the other stream waits.

The relay cannot create a valid alternative sequence or skip a predecessor without the writer's signing key. An observed signed fork is rejected against saved accepted or pending history. This does not provide global consensus between cloned copies of a node key: a malicious writer can maintain separate histories until endpoints compare them, or sign invalid MLS data. Such a packet remains pending and stops the stream for diagnosis; the receiver never silently skips it. Recovery from a compromised writer, rollback of an entire endpoint backup, key loss, and selective withholding remain separate work.

## Encrypted configuration recovery

`ordered::configuration` gives each trusted receiving daemon its own two-node configuration stream. An owner-signed grant binds the cluster anchor, exact initial checkpoint, group and origin digest, and both node IDs and signing keys. Provisioning requires fresh authority at both ends. The grant and key package contain private identity metadata and travel through authenticated invitation or SSH pairing. A hosted bridge must never receive a configuration grant.

Only an established configuration stream may receive, retransmit, or encrypt already accepted signed configuration history with expired authority. Its saved grant and both endpoint keys must still match known membership. Revocation or signing-key replacement disables it. Fresh authority is required to create a stream or refresh encryption keys. This recovery exception lets a full history queue drain even when its quota blocks renewal. It grants no ordinary message-send permission and cannot create a new signed policy. Ordinary data APIs reject configuration streams, and configuration APIs reject data streams. Configuration records never enter the application inbox.

The writer first accepts owner-signed revisions into its local authority history. `next_configuration` then publishes them in order, tracking a separate cursor for each recipient. Each signed record is split into fragments of at most 256 KiB, with its revision, digest, total size, and offset inside MLS encryption. Committed requests return the same packet on retry. A return value of `None` means there is no new history and does not reserve the request ID. Configuration and chat-record fragments fit the Worker proof's 1 MiB frame limit; files beyond current inline limits still need a resource/storage protocol.

The receiver verifies fragment continuity and the complete record's owner signature, predecessor, and revision before changing authority. Known revisions must match retained verified history; conflicting owner-signed forks are rejected. A complete expired revision can advance the checkpoint, but ordinary messaging stays blocked until a fresh revision is reached. Partial records cannot change authority. The final fragment commits authority, history, MLS state, receipts, stream checkpoint, and fragment cleanup in one transaction. An MLS epoch refresh may change encryption keys while preserving both signing identities and membership.

Configuration ciphertext has a separate 8 MiB pending quota, with 3 MiB reserved for a missing predecessor. A full application queue cannot consume that space. Partial records reserve their entire declared size from a separate 8 MiB reconstruction budget when admitted, allowing them to finish even when that budget is full. Completed records release the reservation; retiring a writer removes its pending packets and partial records. Malformed authenticated traffic stalls its stream, and a compromised approved writer can still withhold updates or consume its available quota.

This recovers an expired node that retains its keys, checkpoint, and established stream. It does not recover lost keys or roll back an endpoint backup safely. The sender needs a contiguous retained history after each recipient's initial checkpoint. Retention, stream replacement, and protected distribution of initial grants and key packages remain required for live operation.

## Automatic configuration sync

An explicit machine-local `[relay]` setting starts the daemon's background configuration task. It needs established, owner-authorized configuration streams and no chat turn. Successful signed edits and lease renewals notify the task after commit. Publication persists each encrypted packet before upload; reception verifies the packet, MLS sender, and signed history before changing live policy. A saved pending packet is drained before contacting the relay, so it can finish applying after a restart even while the network is unavailable.

The development HTTP protocol uses a base64url-encoded opaque group ID as its mailbox address:

| Request | Response |
| --- | --- |
| `GET /v1/mailboxes/{group}` | JSON `{"next": N}`, an untrusted next-storage-position hint. |
| `PUT /v1/mailboxes/{group}/{sequence}` with the encoded packet as its body | JSON `{"stored": true, "sequence": N}` on success. |
| `GET /v1/mailboxes/{group}/{sequence}` | Exact encoded packet, or HTTP 404 if unavailable. |

Uploads are limited to 1 MiB, and JSON metadata responses to 1 KiB. The client bounds streamed responses, disables redirects, and sets connection/request timeouts. HTTPS is required except for loopback development origins. The credential comes from a private local file, separate from node/owner keys. The proof relay uses a shared synthetic bearer token; it does not implement account or per-node service authorization. That token authorizes storage only. Possession does not authorize a signed revision or decrypt a packet.

The local Worker persists opaque packets in D1. Its insertion triggers enforce contiguous storage and advance the mailbox head atomically. Exact retries succeed, conflicting bytes and gaps fail. Neither a relay position nor a storage acknowledgment proves recipient acceptance. The sender rejects a position beyond its local history and retains all ciphertext/history after upload, allowing retransmission after relay storage loss. Endpoints verify the requested group and sequence and never use a relay timestamp to order policy changes. The service still sees opaque routing IDs, traffic sizes, and timing.

The dispatcher rotates through batches of up to 32 streams with four concurrent transfers and never holds the RPC store mutex during network requests. It scans at most 4,096 configuration streams plus two data streams per linked peer (up to 1,024 peers), excluding known revoked or replaced peers. Local commits and relay push signals wake it immediately. Progressing transfers continue after 10 ms; errors back off per stream from one to 30 seconds. Retry deadlines remain active while push is connected. Network, storage, verification, and backlog still determine application latency.

The dispatcher also carries chat records, configuration proposals/results, and peer bootstrap records over separate data streams. Invitation-based enrollment and production service limits remain unfinished. Outbound history has local transport caps; verified receiver checkpoints permit bounded endpoint and relay retirement. Full configuration-history retention and separate message/retry retention are described below. Accepted digest/retry metadata, abandoned streams, and total storage still need bounds.

### Push notifications and recovery

Each configured daemon connects to `GET /v1/watch` over WebSocket, using the same origin and private authorization header as HTTP. HTTPS maps to WSS; loopback development origins may use WS. The client does not follow redirects, limits frames/messages to 1 KiB, and bounds handshake and write time. No token is placed in a URL. Browser smoke clients use the existing synthetic-token subprotocol instead.

The development Worker routes successful mailbox writes through a hibernating Durable Object. After D1 storage succeeds, it broadcasts `{"version":1,"event":"changed"}`. New connections first receive `{"version":1,"event":"ready"}`; that signal triggers reconciliation after subscription so a write during connection setup cannot be missed. These untrusted hints carry no group ID, node name, configuration, or message contents. They cannot advance a checkpoint or mark a message delivered. Existing encrypted packet and signed-authority checks remain mandatory.

The client coalesces bursts into at most one wake-up per 50 ms. A healthy channel reconciles every 30 seconds, covering lost signals. It sends `gent-ping-v1` every 15 seconds and requires `gent-pong-v1` within 45 seconds; the Worker responds through its hibernation auto-response API. Invalid frames, socket closure, missing readiness, or heartbeat expiry cause reconnection with backoff from one to 30 seconds. Without a ready push connection the dispatcher falls back to one-second polling. Stopping the dispatcher also stops its notification task.

This proof has one shared-token notification realm and broadcasts to all its connections, capped at 2,048. Participants can observe that some relay traffic occurred, beyond their own stream activity. Production must scope notification realms to authenticated service membership and enforce connection revocation, rate limits, and resource quotas. The local tests exercise the hibernation API but do not prove Cloudflare production eviction behavior, scale, or cost. Mobile OS push and chat wake/resume remain separate integrations.

## Encrypted chat delivery

Invitation or SSH pairing establishes two exact-roster data streams between the owner and a joining node. Automatic peer setup adds the same independent streams between joined nodes. Each stream has one authenticated writer. A remote directory entry never carries a usable MCP credential.

New chat IDs are domain-separated hashes of their hosting node UUID and a random nonce, encoded as UUIDv8. An enrolled malicious node cannot claim another node's unknown chat ID using its own nonce. Legacy random IDs retain their credentials and require an owner-signed cluster/chat/node binding; the owner persists unique assignments and rejects conflicting ownership. Directory updates have monotonic generations, immutable origins, and permanent revocation tombstones. Enumeration policy still filters the chat-facing directory.

Records carry an authority checkpoint, sender registration, and stable sender-scoped message ID. Receivers verify hosting-node ownership, content limits, participants, lifetime, and reply parent. A reply must refer to a locally accepted message with the same exchange and expiry. A record ahead of local signed authority waits for configuration recovery. Current policy governs import and each later inbox read. Remote exchanges allocate 16 messages per sender, 32 total, to bound simultaneous offline replies without a shared counter.

RPC acceptance commits the local message and outbound event together. The dispatcher commits each MLS ratchet step with its ciphertext and stable request ID, then advances the event's fragment cursor. If that cursor write fails, retry retrieves the same ciphertext without another ratchet step. Reception commits the MLS ratchet with a bounded decrypted-frame inbox. A second transaction reassembles the record, imports its queue entries or receipt, and removes consumed frames together. Failed imports preserve the encrypted/decrypted recovery state for retry.

A queued message is checked against current permission inside the encryption transaction. Revocation persists cancellation and sends an encrypted cancellation frame, clearing a partly received record. A cancelled send remains marked revoked if permissions are later restored. Already committed ciphertext remains retained; later revocation cannot retract plaintext previously delivered to an endpoint. Message expiry and current policy still govern inbox access. Only an authenticated receipt from the recipient's hosting node changes delivery status; relay storage acknowledgments never claim chat receipt or completion of work.

Records are limited to 2 MiB and split into 256 KiB fragments, keeping encoded packets within the relay's 1 MiB limit. Inline files remain limited to 1 MiB decoded per message. Pending decrypted frames have a 16 MiB bound; reconstruction reserves at most 8 MiB across partial records. Malformed authenticated records stall their stream. Encrypted stream pruning, total storage quotas, and repair after lost state remain unfinished.

Six runtime tests inject enqueue, fragment-cursor, and recipient-import failures, cancel partial files, reject foreign chat claims and forged replies/receipts, delay messages until configuration catches up, and bound replies queued by both nodes. Two automatic relay tests cover a 1 MiB file, scoped replies, restart, authenticated acknowledgment, outage, policy changes, and directory tombstones. Two authority tests check ID scoping and legacy-certificate substitution.

## Encrypted file objects

`gent-crypto::files` and `gent-daemon::file_objects` provide the encryption and endpoint-storage components for larger attachments. `gent-daemon::file_transport::FileRelay` transfers their ciphertext through a development Worker with D1 reservations and R2 storage. Chat messaging now uses these components through authenticated MCP file tools and a bounded background dispatcher. Inline files remain available with a combined 1 MiB limit.

Each new `seal` call generates an independent UUIDv4 object ID and a random 256-bit key, including when forwarding identical bytes. RustCrypto ChaCha20-Poly1305 encrypts chunks of up to 256 KiB. Its 96-bit nonce is eight zero bytes followed by the chunk index as a big-endian 32-bit integer. The API seals an immutable object once; it does not allow callers to encrypt different plaintext under an existing key and index. Retries must reuse saved ciphertext and its grant. An empty file has one authenticated empty chunk.

Every chunk authenticates the complete manifest, chunk count, and index. The AAD starts with `gent/file-chunk/v1\0`, followed by object ID, filename, media type, and lowercase hexadecimal SHA-256; each UTF-8 field has a big-endian 16-bit byte-length prefix. Next are the plaintext byte length as a big-endian 64-bit integer, then count and index as big-endian 32-bit integers. A complete read verifies the whole-file hash as well as each AEAD tag. Swapped, duplicated, truncated, cross-object, and modified chunks fail authentication or completeness checks.

The public `FileDescriptor` contains only the ID, basename, media type, byte length, and integrity hash. `FileGrant` contains the key and manifest, has no `Debug` or `Serialize` implementation, and requires explicit private encoding. Its versioned JSON parser rejects unknown or duplicated fields, invalid manifests, oversized grants, and malformed keys without echoing secret parser input. Grants are intended for protected local state and encrypted message records. Their possession alone does not authorize chat access. Names, types, hashes, and keys must never be sent as object-storage metadata.

The storage API operates within the caller's SQLite transaction so file reservation, ciphertext, and an enclosing message can commit together. Receiving an authenticated grant reserves the complete expected ciphertext size before accepting chunks. Each incoming chunk is authenticated before storage; duplicates must match exactly. Downloads may arrive out of order and resume after reopening the database. Complete reads require the full verified file. Upload acknowledgments persist separately and mean service storage only. A lost relay copy can be uploaded again using identical ciphertext. The public storage manifest can be reconstructed from saved chunks and the original deadline after restart, without exporting the private grant.

| Endpoint storage limit | Value |
| --- | --- |
| Plaintext per file | 32 MiB |
| Chunks per file | 1-128 |
| Ciphertext per chunk | At most 256 KiB + 16-byte tag |
| Objects per database, including reservations | 128 |
| Reserved ciphertext per database | 256 MiB, including tags |
| Incomplete object lifetime | At most one hour from its local reservation |
| Complete object retention | Caller-selected deadline, at most seven days from its local reservation |

Exact retries cannot change stored keys, manifests, deadlines, or ciphertext. Expired or abandoned objects become inaccessible before cleanup runs. Explicit deletion and cleanup remove their grants and chunks together and release logical quota. These limits bound this component's live objects, not SQLite/WAL file sizes, old backups, or message history. The daemon reaps expired file objects during maintenance and transfer scheduling; the development relay has its own durable cleanup alarm described below. Pending message records can contain another private grant copy, and transport/message history has separate unfinished retention work. Private key buffers and successful decrypted buffers are zeroized on drop; forensic erasure of all temporary copies, database pages, and backups is not established.

Seven crypto tests and nine storage tests cover empty and maximum-size files, manifest/key/chunk substitution, malformed grants, whole-file integrity, restart recovery, upload retry, atomic rollback with an enclosing message, concurrent reservations, quotas, expiry, deletion, missing chunks, schema versions, and separation of public ciphertext metadata from private metadata. Three committed vectors also match Python `cryptography` independently, including a nonzero chunk nonce and an empty file. Reproduce them with `python3 scripts/file_object_vectors.py --check` in an environment with that package installed.

### Chat bindings and host files

`gent_file_import` reads a basename from the authenticated chat's private `outbox` folder, returned by `gent_file_paths`. Imported objects belong only to that chat and expire after seven days. A send, reply, or relay operation accepts `file_ids`, checks current source-file access and destination permissions, and seals a new object for each reference. IDs, keys, manifests, message records, and outbox events commit together. The input IDs form part of the retry fingerprint; an exact retry returns the original message without creating another object.

Messages expose only `FileDescriptor` values in `attachments`. Empty attachment fields are omitted to preserve existing inline-message encodings; upgrade paired nodes before using file-object messages. An explicit private wire adapter places grants and ciphertext manifests inside the MLS message record. Import checks descriptor equality, chunk lengths/count, original message expiry, object uniqueness, sender/recipient binding, and exchange permissions. A retained digest of the private grant list rejects conflicting duplicate records even after the file object is reaped. Objects cannot be rebound to a second message.

`gent_file_status`, chunk reads, image views, export, and forwarding require fresh signed authority, an active local registration, and ownership of the staged object or participation in its authorized message. Current ordinary permissions and message expiry govern every access; legacy relay turns also retain their original grant checks. Guessed and unauthorized IDs share an unavailable error. Revocation prevents subsequent access through Gent; it cannot retract bytes an authorized host previously exported or copied.

`gent_file_read` reads and authenticates only the selected chunk, at most 256 KiB of plaintext, from an object already marked complete. Completion requires whole-file verification on receipt or trusted local sealing. A chunk read does not rehash other stored chunks. Callers reassembling bytes must verify the complete descriptor length and SHA-256. `gent_file_view` rereads and verifies the whole file before returning original raster bytes, bounded at 4 MiB to fit the local RPC frame after base64 encoding. Supported media types are source declarations, not image-decoder validation. MCP sends descriptor text and one image block without a duplicate base64 text field. Both tools expose no file key, path or persistent plaintext export. Remote gateway responses are plaintext to the authenticated provider and user node; the central relay still receives ciphertext only. Optional outgoing download links have the separate bearer-delegation boundary described below; provider-native file references remain unverified.

Optional [host file inputs](gateway.md#import-host-provided-files) require exact owner-selected HTTPS origins per authenticated host. URL arguments remain untrusted: the fetch validates and pins public DNS answers, requires TLS, rejects redirects/proxies/compressed or oversized bodies, and sends no Gent credentials, cookies or referrer. The selected origin permits file requests to that origin; it does not authenticate the provider account or prove that a human uploaded the file. No provider allowlist is embedded. Hosts still supply the conversation/user identity and external file ID faithfully.

Downloads are capped at 32 MiB, ten seconds including DNS, two concurrent operations globally and one per host with a one-second attempt interval. The accumulated download and local body buffers are zeroized on drop; this does not cover transient HTTP/TLS library buffers. The daemon's protected socket accepts a separate bounded binary exchange after authenticated preflight; two ingress slots remain held through any continuing preflight or commit task after a socket timeout. A complete length/hash check precedes atomic sealing, binding and retry-record storage. Authority is checked at preflight and commit. There are no temporary plaintext files, externally decodable in-memory RPC operations, or changes to the immutable fresh-key sealing API. Existing object quotas and retry-record cleanup apply. This bounds the import buffers; it is not a global filesystem or bandwidth budget.

The retry record uses a domain-tagged hash of source identity/name/type plus the content digest, scoped to the local chat and request ID. URL secrets and raw provider file IDs are not persisted. Completed retries return the original descriptor without contacting the source and cannot observe a later source mutation; a changed source identity/name/type is rejected. The local binary header additionally commits to the incoming length/hash, rejecting conflicting competing transfers. Registry authorization is checked again after download, before local transfer; gateway revocation and daemon commit are separate transactions. New chat operations remain subject to current daemon authority, and revocation cannot retract an already committed result or previously returned bytes. Actual provider attachment provenance and acceptance remain unverified.

Optional [download links](gateway.md#download-links) deliberately delegate access to one file to the URL holder. The owner must select each host with `--file-downloads`; authenticated MCP minting still requires host-owned identity and any configured mTLS policy. Redemption requires the bearer URL, without a host token or client certificate. This exposes authorized plaintext to its holder through the user's gateway. The central relay continues receiving only encrypted node traffic. Links can leak through host/browser history or recipient sharing, and do not establish E2EE against the provider or URL holder.

Tokens use HMAC-SHA256 with a domain prefix and the existing private chat credential. They bind the registry UUID, host, hashed chat binding, file UUID, gateway origin and timestamps, plus OAuth grant/user scope when applicable. No file key or chat credential appears in the URL. Tokens are stateless, last at most five minutes and survive restart within that lifetime. Redemption never creates a binding. It checks the retained binding, host/grant state and expiry, user pin and durable clock watermark. OAuth refresh preserves an existing link; revoked grants cannot regain it through a new authorization.

The gateway checks live file access on status and every chunk, verifies the full length/hash before returning bytes, then checks registry and file access again. Two bounded payload slots remain held by the HTTP byte buffers through response consumption or drop, including clones. The 32 MiB file limit and existing request/connection deadlines remain. HEAD checks metadata/access without full-byte verification. No-store, attachment disposition, nosniff and sandbox headers limit browser handling; the source's media type is not image-decoder validation. Authorization and HTTP delivery are separate operations: revocation cannot retract an admitted response or previously received bytes. Whole-buffer zeroization does not promise erasure of all RPC, TLS, socket or recipient copies.

The file dispatcher uses one reservation to upload up to four missing chunks per object per pass, with batches of at most 16 objects and four concurrent transfers. A two-second slice ends the burst after the current upload. It holds no Store mutex during HTTP, and stalled object requests cannot block configuration synchronization. Idle file discovery runs once per second; completed uploads wake message publication. It rechecks authorization before reading upload bytes and after network completion before committing progress. Message publication waits for all upload acknowledgments. Recipients can then fetch missing chunks from an authorized sender over QUIC or from cloud storage. During a download, each chunk authenticates before storage, and the complete hash verifies before export. Upload reconciliation repairs a lost relay copy with identical ciphertext and its original deadline. Retries back off from one to 30 seconds; completed uploads reconcile every 30 seconds. Missing download chunks use retry backoff. Neither relay hints nor file completion constitute a chat receipt.

`gent_file_export` writes verified plaintext under this chat's private `inbox/<object-id>/` folder and returns a local path. Directory-relative opens reject symlinks; input files must be regular, owned by the node user, and have one hard link. Export publishes a fully written temporary file without overwriting an existing destination. An existing matching export is reusable; edited files fail. Export reservations and recovery are described below. Import/export paths are on the daemon machine; this is not a web upload API or a sandbox for hosts with the OS user's shell authority.

Successfully imported/exported plaintext copies now have a local retention ledger independent of encrypted-object rows. Each entry stores the chat/path slot, file identity, size, nanosecond modification/change times, content hash, and expiry. Reimporting an unchanged source retains the latest expiry. Owner commands report file usage and preview/run cleanup; MCP credentials cannot invoke them. Startup and 15-minute maintenance process up to eight due copies per pass, including when authority is expired or the node has lost membership.

Cleanup opens directories relative to protected directory descriptors, rejects links and nonregular files, checks the recorded snapshot, then renames the file to a unique ledger-bound recovery name without replacing another path. It verifies identity and hash again before unlinking and synchronizes directory changes before committing the ledger update. After a crash or database rollback, the next pass can finish a matching recovery file or forget an already missing copy. A replacement at the original name is not deleted. Modified files are restored without overwriting replacements, or preserved at their recovery path with owner-visible diagnostics. Blocked and preserved entries retry after 15 minutes. This assumes a trusted OS user; arbitrary concurrent writes through existing handles and forensic erasure are outside the guarantee.

Old-version untracked files, unimported source files, abandoned old-version temporary files, and empty folders require separate user/host cleanup. The handoff admission limits below count recorded snapshots and reserved exports rather than all current filesystem bytes. Encrypted-object quotas include both staged and sent copies. File cleanup leaves import fingerprints, message/file-proof records, and stream history to the separate message-retention and transport-compaction rules below. Aggregate disk bounds remain unfinished. These tools do not supply hosted attachment access, GUI file pickers, or automatic host execution.

Five chat-file tests, one adversarial network test, and two automatic-dispatch tests cover access isolation, empty and multi-chunk files, retry/restart, fresh forwarding keys, corruption, conflicting grants, permission and relay revocation, link/path rejection, transactional rollback, and relay storage loss. Six retention tests add dry-run, changed/replaced/linked file preservation, directory substitution, interrupted rename recovery, recovery-name collisions, database rollback, retry retention, deadline extension, and bounded batches. All pass on Linux and macOS; a process proof exercises CLI/MCP cleanup and startup recovery on both. A live Worker test passes 32 MiB chat round trips on both OSes, and a physical Linux-Mac MCP proof passes 2 MiB files. Both real Codex/Claude pairings also pass native 3,073,103-byte PNG/SVG inspection, revision, and faithful file relay after daemon restarts.

### File-object relay protocol

All object routes require the relay's configured transport credential: a shared development token or a node credential in the separate service-backed build. IDs are canonical UUIDv4 strings. The public manifest contains `version: 1`, an ordered `chunks` array of `{bytes, sha256}` entries covering ciphertext and its AEAD tags, and `expires_at`. It contains no filename, media type, plaintext hash, chat identity, or key. File sizes, opaque IDs, ciphertext hashes, deadlines, and access timing remain visible to the service.

| Request | Behavior |
| --- | --- |
| `PUT /v1/objects/{id}` | Reserve the complete object using its public manifest; exact retries preserve the deadline and progress. |
| `GET /v1/objects/{id}` | Return the manifest, sorted uploaded indices, `complete` hint, and fixed `upload_until` deadline. |
| `PUT /v1/objects/{id}/{index}` | Store the exact reserved ciphertext chunk; conflicting bytes fail. |
| `GET /v1/objects/{id}/{index}` | Retrieve a stored chunk as `application/octet-stream`, with caching disabled. |
| `DELETE /v1/objects/{id}` | Retire the object and remove its R2 chunks; repeated deletion is safe. |

D1 reserves up to 128 active or deleting objects and 256 MiB of ciphertext, including AEAD tags, in the shared development realm. SQL enforces these aggregate limits. Manifests are bounded to 16 KiB and chunks to 256 KiB plus a tag. An incomplete reservation lasts at most one hour; its overall expiry is at most seven days from creation. Neither deadline extends on retry. Completed objects can be repaired with identical ciphertext until their original expiry.

A Durable Object serializes mutations across D1/R2 awaits. Conditional R2 writes prevent replacement; an existing chunk must match the retry. Progress commits only after R2 acknowledges storage. If that progress write is lost, uploading the same chunk reconstructs it. Expired, abandoned, and deleted objects remain inaccessible. Cleanup retains reserved quota until R2 deletion succeeds, then keeps a tombstone until the original expiry plus one day. At most 4,096 active/deleting/retired records are retained. Durable alarms process cleanup in bounded batches without chat traffic and retry interrupted deletion. This is logical retention, with no forensic-erasure guarantee.

The Rust client shares the existing private-credential, safe-origin, timeout, and no-redirect transport setup. It bounds response bodies, validates progress shape, compares reservation acknowledgments to the original manifest, and verifies chunk lengths and ciphertext hashes. The private grant's AEAD and whole-file hash still establish content authenticity. Relay progress never grants chat access or proves delivery. Two client tests reject malformed progress, changed manifests, corrupt/oversized responses, and redirects that could forward credentials. Two protocol tests cover framing and progress bounds.

An opt-in native test transfers a 32 MiB object and an empty file through the local Rust Worker on Linux and macOS. It reopens sender and receiver databases, reconstructs the original public manifest, retries a lost upload acknowledgment, resumes partial downloads, and verifies the decrypted bytes. It is separate from the default test suite:

```sh
GENT_TEST_RELAY_URL=http://127.0.0.1:18787 \
GENT_TEST_RELAY_TOKEN_FILE=/absolute/private/relay.key \
cargo test -p gent-daemon --test file_transport --locked \
  wrangler_transports_encrypted_file_objects_with_endpoint_restart -- --ignored
```

The development Worker also passes HTTP tests for conflicting/concurrent uploads, declared and streamed body limits, both aggregate quotas, alarm-driven expiry without HTTP traffic, abandoned uploads, interrupted deletion, and tombstones. Production account/node authorization and storage billing remain unfinished. This proof creates only local D1/R2 state and does not deploy a messaging service.

## Boundaries still to implement

Key packages contain identity metadata and must travel inside an authenticated, encrypted enrollment or distribution channel. They must not become a plaintext public directory. MLS Welcome messages protect their group information, while ordinary MLS headers still expose opaque group IDs, epochs, sizes, and timing. The surrounding routing protocol must account for this metadata.

Node authentication does not authorize one chat to read another chat's messages. MLS inbox/outbox accessors are for trusted local code. The live RPC path and remote import check signed policy and bind each registration to its authenticated hosting node. Trusted daemons can read records addressed to their node; MCP callers receive only their permitted directory and inbox.

Configuration streams belong only to trusted daemons; messaging streams serve separately authenticated endpoints. Larger-file transport and scoped grants are described above, and invitation pairing is implemented. Periodic epoch refresh scheduling, signing-key replacement, lost-state recovery, hosted/mobile trust boundaries, and independent security review remain required before production use.

## Automatic peer mesh

A joined daemon discovers peers from signed cluster membership and exchanges MLS key packages and Welcome packets through its existing encrypted owner link. The owner forwards each record over the intended peer's encrypted owner link. It binds the origin to the authenticated sending node; recipients accept forwarded records only from their configured configuration writer. Both node IDs and their current signing keys determine a pair's stable bootstrap identity. The service receives only encrypted packets, including for key packages, node identities, and routing inside these records.

Each endpoint independently verifies the peer's key package against current signed authority. A Welcome must have the peer's valid packet signature, the matching MLS creator, and exactly those two nodes in its roster. A third node's valid package or Welcome cannot substitute for the peer. Each direction has a separate single-writer stream. The owner sees bootstrap metadata as a trusted cluster node but receives neither application group keys nor peer messages. Established streams use the relay directly, and ordinary chat enumeration, send, receive, reply, and delivery rules still apply.

Both nodes offer a package, create their outgoing stream from the other's offer, and join the incoming Welcome. Deterministic request IDs and persisted cryptographic operations make each step retryable after a crash. Source offers commit with their outgoing events. Owner forwarding commits with the job result; endpoint Welcome responses commit with the saved outgoing group and job result. Joining may commit before its job marker, so a retry verifies and reuses the same origin. Installing both streams and announcing existing local registrations is atomic. Configuration recovery and existing stream delivery continue if peer maintenance encounters an error.

Bootstrap overtaken by node revocation or key replacement is discarded. The dispatcher rechecks signed membership before sending and importing ordinary messages; a bootstrap grant does not override chat policy or expiry. Current state can remain valid during an owner outage only until its existing lease expires. Fresh peer setup requires the owner to forward bootstrap records. Replacing lost endpoint state or signing keys and recovering expired unused key packages remain separate recovery work; this version does not silently replace established links.

Maintenance prepares at most eight peer offers, processes eight due jobs, and installs eight completed links per pass. Pending jobs have a per-node count limit of 8,192, bounded payloads, and retry backoff capped at 32 seconds. While jobs are pending, idle reconciliation pauses are capped at one second; network and processing time can add delay. Setup errors are retained locally for retry and logged when they change. Completed jobs, packages, streams, and ciphertext history are retained. The full mesh grows quadratically with cluster size; large-cluster scaling, pruning, aggregate quotas, and user-facing repair commands remain unfinished. `gent nodes` reports established links separately from remote presence.

## Host conversation bindings

The optional `--host` MCP modes select local credentials from host-supplied metadata. Codex uses each call's `threadId`, preserving fork isolation even when threads share a session tree. Claude Code uses a `PreToolUse` hook to record the current session and optional subagent identity as a hashed binding reference, together with a digest of the exact tool call. The server requires the matching tool-use ID and an unexpired handoff for every request. It never falls back to the MCP process's startup session or a previous call's identity. The hook does not approve actions or change communication policy.

Credentials remain in private files scoped to node, cluster, host, and conversation. Symlinked, hard-linked, or shared credential/handoff files are rejected. A lock protects initial credential creation; each active binding retains an exclusive lock. Handoffs retain hashes, timestamps and an optional chat title for registration, expire after ten minutes, and have a 4,096-record limit. The title is a display label, never an identity selector. No tool arguments, conversation message text or transcript path is persisted in the handoff. Each MCP connection can hold 128 bindings. Calls reject undeclared tool arguments, including attempts to provide a session selector through model-controlled arguments. Current MCP per-request client information and older initialization metadata are both supported.

These are continuity checks on an owner-configured local stdio connection. Client names, thread IDs, and hook inputs are not remote authentication, and a chat with unrestricted filesystem or shell access has the trusted OS user's authority. Generic clients can still use explicit credential files. [Setup and limits](local-proof.md#host-conversation-bindings) distinguish verified CLI flows from untested GUI surfaces.

Native children receive separate Gent bindings and permission checks. That separation covers Gent tools: a child's directory, inbox, reply rights and revocation do not inherit its parent's registration. Host-controlled context remains shared according to the host's own behavior. A host can copy parent context into a child or expose a child's report to its parent, including content obtained through Gent. These bindings do not make a native chat tree a confidentiality boundary.

## Daemon services

The CLI installs services for the current OS user through systemd or launchd. Service definitions contain executable and state paths; keys and RPC credentials remain in the protected state directory. Definitions must be private regular files owned by that user, with matching Gent metadata and contents. Lifecycle commands reject edited definitions, symlinks, hard links, and files belonging to another state directory. A per-state lock serializes mutations. Authenticated RPC status supplies the daemon PID, which must match the service manager before Gent controls a running daemon. These checks prevent accidental changes to unrelated services; the OS user remains trusted.

Uninstall retains keys, configuration, SQLite queues, and bindings. SIGTERM stops the daemon gracefully. Status extracts selected lifecycle fields from manager output without returning inherited environment values. Logs remain local, in the systemd journal or a private macOS file; macOS log rotation is unfinished. See [daemon services](local-proof.md#daemon-services) for startup/session limits and upgrade behavior.

## Message retention and replay admission

New sends, replies, file imports, and relay requests use canonical RFC UUIDv7 request IDs from `gent_request_ids`. The ID must be less than 24 hours old at first acceptance and at most 60 seconds ahead of the daemon clock. A retained result is checked before new-ID admission, preserving identical retries after that window, including accepted UUIDv4 requests. File-import retries also require the original source bytes and an accessible object; an expired file cannot be restored by retry. Owner configuration, pairing, MLS, and stream-operation IDs retain their separate contracts.

A singleton request clock stores the greatest committed observation. RPC execution, incoming event import, and history maintenance advance it transactionally. Reopening the database or moving the system clock backward cannot admit a pruned old ID again. This does not protect against restoring an older database backup, and other transport/authority paths still use wall-clock time. A large erroneous forward jump can reject IDs and expire history; clock correction/recovery needs a separate design.

Remote UUIDv7 admission compares issuance to the authenticated message's creation time, so an already accepted message can arrive later within its exchange lifetime. Creation may not be more than 60 seconds ahead; expiry must follow creation by at most 24 hours. Once an exchange is retired seven days after expiry, neither its original lifetime nor a rewritten current lifetime can make its old request ID deliverable. During upgrade, unknown legacy remote requests are allowed only before a fixed first-upgrade deadline of 24 hours plus 60 seconds, with creation at most 60 seconds after that upgrade and expiry no later than the deadline. Old legacy exchanges cannot retire before the grace ends. The deadline persists across restarts. Unknown legacy local requests are rejected immediately; upgrade connected daemons and clients together.

A cleanup transaction retires up to eight complete expired exchanges, including relay turn references, message-bound file objects/grants, file-proof digests, rejection records, and message retry fingerprints. It also retires at most 256 dead import retry records and 128 expired relay selections without remaining turns. Import retry deadlines are indexed and backfilled during schema upgrade so newer IDs cannot permanently occupy the cleanup scan. New work has limits of 8,192 messages, 256 MiB of serialized message payload bytes, and 16,384 import retry records. Existing exact retries bypass admission quotas. Storage failures roll back the message, exchange, object, and queue changes together. Full incoming queues retain their decrypted record for a later attempt, potentially delaying that stream.

Pending outbound message events become empty-body cancellations with their original ID, peer, and fragment offset. Even offset zero can have an MLS fragment committed before a failed cursor update; deleting that event would strand partial data on the receiver. Cancellations survive restart and clear partial reassembly through the existing ordered transport. Late receipts for absent messages have no effect; receipts for retained messages still require the exact hosting nodes.

These limits cover Gent messages and chat retries. Node event queues and deduplication have the additional limits below. Ordered packets and replay evidence have separate retention rules. Owner/configuration-edit results remain retained. Native plaintext handoffs have the separate admission and cleanup rules below. Database pages have the separate allocation limit below. These limits do not erase provider history, exported copies, snapshots, or backups. Logical deletion does not establish forensic erasure.

## Node event queues and deduplication

Schema version 8 adds retention metadata to outbound events and their completed-event retry records. Completion here means all fragments were encrypted and the durable queue cursor committed. It does not mean relay upload, receiver storage, chat acknowledgment, or task completion. The MLS outbox independently preserves unconfirmed packets for offline delivery.

New message and receipt events retain their deduplication record until seven days after the message expires. Negative receipts for legacy IDs remain until at least seven days after the fixed upgrade grace ends, since those IDs have no embedded admission timestamp. Admission and cleanup use the committed request clock. A stale local message snapshot cannot recreate an event after that deadline, even if the wall clock moves backward. Remote messages with inadmissible request IDs are discarded without creating negative receipts; otherwise rewritten creation/expiry times could repeatedly extend receipt work. Valid requests denied by current policy still receive a negative receipt within their retention period. An expired message beyond retention produces no further receipt.

`gent history clean`, startup and periodic maintenance remove at most 256 expired sent-event records per pass. New enqueue attempts also clean one batch before checking capacity. Pending events are never deleted by this cleanup. Message-history cleanup preserves their cancellation cursor and retention deadline, including a packet committed before a failed cursor write. Completion records that cancellation with the same deadline; a later pass can remove it. Cleanup, message history and clock updates share the caller's transaction, so a failed delete rolls back the whole operation.

Registration announcements store the greatest queued generation for each chat and peer. The generation and its durable event commit together. An older or equal generation cannot requeue, and completing a new announcement does not add a per-event tombstone. At most 65,536 chat/peer generation records are admitted. Existing pairs can advance when that table is full; new registrations that need another record fail atomically. Generations remain necessary to suppress old announcements and are not expired.

Message/receipt traffic and configuration/mesh/registration traffic have separate admission reserves: each permits 16,384 queued events, 128 MiB of encoded event bodies, and 131,072 retry slots. Slots count completed records plus pending non-announcement events, reserving space for their eventual cursor commit. Retained exact duplicates bypass admission quotas. A full message reserve does not consume configuration-event capacity; delivery still depends on the existing streams and their unconfirmed history. Queue, acknowledgment, registration, proposal and result changes roll back if enqueue fails.

Legacy completed records and pending events receive no inferred deadline. Their original deduplication behavior survives migration, and unclassified legacy rows count against both reserves. Existing oversized databases keep their work and reject new admissions until capacity is available. Configuration and mesh event IDs have no bounded first-use window, so their completed records remain within the control retry cap. Configuration edits have the separate limits below. Peer setup jobs have the separate limits below. Accepted authority digests have the separate revision limit below. Database pages have the allocation limit below; aggregate filesystem quotas and endpoint recovery remain unfinished. Restoring an old database backup remains outside these replay protections.

## Configuration edit storage

Schema version 9 stores a compact summary for each new configuration edit. Origin/request identity and input fingerprint are immutable. A completed result retains its deciding writer; a pending request's writer identifies its current delivery route. Summaries preserve the operation and status fields (node name or relay grant ID). Large policies and replacement configurations have no full copy in this permanent log.

Schema 20 additionally retains the full input of each local pending proposal in `configuration_pending`, independently of event queues and encrypted transport. Transport acknowledgment can retire ciphertext while the owner still has an unapplied request; the originating node must retain enough information to reroute that request during a future owner handoff. Request admission, payload retention and event insertion share one transaction. An authenticated result releases the payload in the same transaction that records the result. A failed release rolls back completion. Completed retries do not recreate the payload.

Pending payloads have separate limits of 4,096 records and 64 MiB, with a 2 MiB per-record bound. `gent history` reports usage, limits and missing legacy payloads under `configuration_edits.pending_payloads`. Queued `gent config request` results include `payload_retained`; the full contents remain private endpoint data. Exact pending retries verify the original fingerprint and can restore missing legacy contents without applying an edit or replacing a conflicting retained body. Already retained retries work at capacity. This retention alone does not reroute a request or activate a successor.

Startup and maintenance recover at most eight missing payloads from full legacy edits or still-queued events, using a durable cursor so unavailable old contents cannot starve later recoverable requests. A full payload cache does not block startup or result receipt. Event retirement also retains a configuration request before deleting its final queued fragment. Legacy compaction preserves pending inputs in the payload table before replacing them with summaries. If an older node already retired its local input, Gent reports the payload as missing; an exact resubmission can restore it. It does not invent a policy from its summary. Missing current-schema payload tables fail startup instead of silently recreating empty storage.

Schema 22 records delivery routes across owner epochs. After [successor activation](owner-succession.md#live-activation), origins reroute up to eight retained inputs per pass, atomically changing their route and cancelling old queued requests. Epoch-bound event IDs permit delivery to a previously used node without replaying an old transport ID. Historical results retain the original deciding writer; pending results from retired routes cannot decide the request. Authenticated decision adoption preserves both nodes' retry evidence even when their union exceeds ordinary admission capacity. New admissions then remain closed, while existing pending work can finish.

Retired writers retain late undecided inputs in a separate archive limited to 4,096 records and 64 MiB, reported as `configuration_edits.retired_inputs`. These bodies authorize no execution. Archive exhaustion rolls back incoming processing; automatic recovery and cleanup from that archive remain unfinished. Missing origin payloads are still reported as missing.

`gent history` reports edit counts, pending results, legacy bodies, stored bytes and reserved bytes. New admissions are limited to 65,536 records and 64 MiB of logical field bytes, including an 8 KiB encoded-result reservation for every pending request. Completion validates the result size and consumes that reservation, so a full log cannot prevent an admitted request from recording its outcome. New rejection reasons are truncated at a UTF-8 boundary to at most 1,024 bytes; the reservation includes worst-case JSON escaping. Existing legacy results remain unchanged.

Startup, periodic maintenance, new edit admission and `gent history clean` compact at most eight legacy bodies per pass. `--dry-run` verifies and reports the same candidates. Compaction checks each full input against its saved fingerprint before replacing it; it preserves row ordering, results and pending status. Historical rejected inputs are not revalidated against current policy rules. Corruption or a failed write aborts the enclosing transaction. Admission failure also rolls back any signed revision, proposal and response changes.

Exact retained retries bypass admission and compaction. Repairing a missing legacy pending payload requires available payload capacity. Configuration request IDs have no bounded first-use window, so their fingerprints and outcomes cannot safely expire: deleting them could execute an old edit again. Existing oversized logs retain all retry records and allow pending results to complete, but reject new admissions until sufficient capacity exists. Compaction may release log byte capacity; it never releases record slots, and pending payloads stay until their results commit. Automatic owner lease renewal does not create an edit record. These limits exclude SQLite indexes/pages, transaction journals, mesh jobs, accepted authority digests, provider history and total disk usage. They do not establish forensic erasure or protection against restoring an old database backup.

## Peer setup job storage

Schema version 10 stores a SHA-256 input fingerprint for each admitted mesh bootstrap job. Pending jobs retain their complete envelope. When a forwarding or stream-setup step commits, its full job body becomes empty in the same transaction as the durable outbound event or saved stream association. Completion means that local step is durable; it does not assert that the remote peer has installed its link. Outbound events, encrypted packets and saved stream associations preserve the work still needed for delivery and link installation.

Exact repeated signals compare against the retained input fingerprint, including after restart; changing the key package or Welcome under the same signal ID is rejected. These deterministic IDs have no expiry, so completed retry records remain retained. Legacy pending records keep their full inputs and original retry behavior. Before processing or compacting a stored body, Gent verifies its serialized form, derived job ID and saved fingerprint when present. New fingerprints cannot prove that a legacy body was unchanged before migration; the private endpoint database remains trusted.

Admission permits 8,192 pending jobs, 65,536 total job records and 128 MiB of logical field bytes per node. Every pending job reserves 1 KiB for its retry error, counting a larger existing legacy error in full. New errors truncate at a UTF-8 boundary. Pending error updates and completion require no new quota admission. Existing duplicates bypass quotas, and oversized legacy databases retain their work while rejecting new admissions. Completing jobs releases body bytes and pending slots; permanent retry evidence continues to consume total record slots.

`gent history` reports these limits, pending jobs and completed bodies awaiting compaction. Startup, periodic maintenance, new admission and `gent history clean` compact at most eight old completed bodies per pass. Preview verifies the same candidates without modifying them. Compaction preserves row ordering, completion state, attempts, retry time and legacy errors. Pending bodies are never compacted. Corruption or a failed write rolls back the enclosing cleanup/admission transaction. A failure after MLS group creation but before the job commits leaves the full pending envelope; deterministic cryptographic retries recover the same stream without consuming another key package. These limits exclude mesh peer associations, raw MLS records, indexes/pages, transaction journals and total disk usage. Logical deletion does not establish forensic erasure.

## Ordered transport storage

Ordered sends retain one signed packet plus its request fingerprint and association. The redundant raw MLS outbox column becomes empty in the same transaction that saves the packet and advances the stream. An unretired exact retry validates the original fingerprint, verifies and decodes the saved signed packet, and reconstructs the original MLS bytes without advancing a ratchet. Standalone raw MLS groups retain their bytes. Schema version 11 prevents older binaries from opening state without enforcing the accepted-revision limit and understanding compacted mesh jobs and edits, event retention, allocated transport requests, retired packets, and compacted configuration history.

For each data or configuration stream, the origin digest and most recent 128 accepted position digests are retained. Wire receipts now record their ordered sequence and retire with that window. Stream advancement, new receipt insertion, evidence deletion, and MLS state commit together. On upgrade, old receipt hashes without sequence metadata can retire for ordered groups: the saved stream head prevents replay at old positions, raw receive APIs refuse ordered groups, and consumed MLS generations cannot be accepted under a new position. Receipts for unsequenced groups are preserved.

An authenticated packet matching retained evidence returns `Duplicate`. A non-origin packet below the retained evidence window returns `Retired` when its digest is no longer available. `Retired` never queues or decrypts the packet and does not assert that its bytes match the original. Signature and current writer authorization are checked first; conflicting recent or origin digests still fail. The durable head hash continues to enforce the next predecessor. Deleting old evidence forfeits detection of forks confined to that discarded prefix; it does not permit that prefix to change accepted state. Restoring an older endpoint backup remains outside these rollback protections.

Outgoing data packets have a per-node cap of 65,536 records and 512 MiB of encoded signed packets. Configuration packets have a separate reserve of 65,536 records and 128 MiB. New encryption/publication rolls back when its class is full, including MLS state, stream head, configuration cursor, and retry records. Unretired exact retries remain usable. Retained packets include Welcomes and epoch changes. Existing databases above a cap retain their records and reject further publication in that class. Retired tombstones do not consume these packet quotas.

Each class also admits at most 131,072 ordered retry records, counting origins, unconfirmed packets, and legacy tombstones. Existing oversized databases retain their records and reject new publication; exact retained retries still work. Configuration has its own reserve, so a full data queue cannot consume its metadata capacity. These are logical row limits, not total SQLite or disk quotas.

The daemon allocates UUIDv7 transport request IDs inside the transaction that encrypts and saves a packet. In the MLS operation namespace, a previously unknown UUIDv7 requires an allocation bound to the exact operation, group and body. Caller-selected new IDs use UUIDv4 or deterministic UUIDv8. Key-package creation rejects unknown UUIDv7 IDs, and configuration publication rejects an externally supplied UUIDv7 without a retained configuration result. Retained pre-upgrade retries, including UUIDv7, continue to use their saved result and remain legacy records. Chat-facing UUIDv7 requests use the separate admission rules above; they are not transport allocations.

Data allocations additionally bind the durable event ID, fragment offset, and part/cancellation kind. Retries recover that binding after restart; an already encrypted pre-upgrade deterministic fragment takes precedence. No allocation is committed without its packet. An event queued while offline acquires an ID when encryption starts, and an unconfirmed retry has no timestamp-based expiry. Configuration allocation, encryption, publication cursor and retry association commit together.

Every stream advancement trims a bounded batch of old evidence. Startup, 15-minute maintenance, and `gent transport clean` additionally compact at most eight redundant ciphertext copies and delete up to 256 old digests and 256 eligible wire receipts per pass. `--dry-run` verifies and reports the same candidates without deleting them. Legacy databases can need several passes before reaching the replay window. Compaction compares duplicate bytes with the verified signed packet before clearing the raw copy; disagreement or a storage failure aborts the transaction.

Unconfirmed outbound packets remain available for offline catch-up, including positions whose local replay evidence has retired. A relay upload acknowledgment cannot authorize local deletion. On an immutable two-node stream, the receiving node signs only its committed head with the domain `gent/stream-receipt/v1`. The bounded canonical checkpoint contains a version, opaque stream ID, position, digest, and signature. It contains no node identity, key, chat ID, message body, or task outcome. A staged packet or gap cannot advance it. Committed plaintext and partial configuration records remain durable even before application processing completes.

The sender binds the checkpoint to its pinned peer or owner-signed configuration grant, checks current authorization and signature, and matches its digest to the committed outgoing packet. A monotonic saved checkpoint and retirement commit in the same transaction. Data checkpoints require fresh authority; configuration checkpoints use the existing expired-lease recovery grant and still reject known revocations. Multi-reader streams cannot use this retirement mechanism. Checkpoints confirm endpoint storage only; `gent_ack`, relay progress, and task completion retain their separate meanings.

Each confirmation or maintenance retirement operation processes at most 256 confirmed packets. For allocated requests it deletes the packet, fingerprint, allocation and configuration retry association together. The now-unknown UUIDv7 cannot initiate another operation, even with changed content, another operation kind, or a backward clock change. Origin packets and legacy retry tombstones remain; a tombstone rejects its old request instead of producing new ciphertext. Chat-level retained retries still return their original message result. Both legacy and allocated IDs for the current pending fragment and its cancellation are protected so a crash between encryption and saving the daemon's cursor can recover its exact packet. Dry-run reports eligible retirement without changing storage. Logical deletion releases packet and metadata capacity but does not establish forensic erasure.

The daemon publishes checkpoints to the development relay and requests relay retirement only after local verification. Relay checkpoint uploads alone do not delete packets. The relay stores a monotonic retirement floor and deletes at most 256 packet rows per request; a sender can reconstruct that floor after relay storage loss and append its unconfirmed suffix. Duplicate checkpoint uploads do not send wake-up notifications. The relay has no receiver keys and does not verify signatures; its shared development token permits denial of service, including deletion, but cannot authorize endpoint retirement or modify authenticated plaintext.

Restoring an old receiver backup after retirement requires endpoint recovery; skipped history is never silently accepted. Allocation admission likewise assumes the current sender database, not an old backup. Stream replacement after key/state loss, accepted authority digest retention, owner-edit retries, raw groups, endpoint metadata, plaintext, transaction journals, and total filesystem usage remain unfinished or outside these transport caps. Event deduplication has the limits above; legacy transport tombstones remain within their admission cap. Production mailbox authentication, aggregate quotas, and abandoned-stream expiry also remain outstanding.

## Configuration history compaction

Full signed configuration records supply the publication queue. Accepted revision digests supply older authority checks. Schema version 6 separates these: every newly accepted signed revision saves its digest with the authority transaction. Compaction verifies an older full record against the owner signature and any saved digest, saves the digest if needed, and deletes that full body in the same transaction. The current signed authority remains intact.

Cleanup targets the latest 64 full records plus every revision still needed by an active outgoing stream. A partially published record stays until its last fragment is encrypted and the publication cursor advances. Already encrypted packets support offline catch-up under the separate transport quotas and receiver-checkpoint rules. Incoming duplicate configuration streams compare older revisions to their saved digests. Delayed application records and configuration-edit results use the same comparison; live membership and permissions are still checked against current authority.

Enrollment records a per-node/key history pin before returning its bootstrap snapshot. Retries keep the earliest required revision. The pin remains until an installed data link and a verified configuration checkpoint establish that the peer caught up to current configuration, or membership removes/replaces that key. Older owners conservatively pin enrolled peers during migration because old databases did not record interrupted joins. Joined runtimes clear these migration pins after loading their node-only identity; they cannot issue enrollment snapshots. A stalled join can therefore retain more than 64 full records, intentionally preserving recovery.

Full history admits at most 8,192 records and 256 MiB of encoded bodies. Capacity failure rolls back the authority update, digest insertion, cleanup, and publication/projection work. Revocation can release history required only by the revoked peer within that transaction; other peers may still require it. Existing oversized databases keep their records and reject additional updates until enough eligible history is compacted. Each update, startup/periodic maintenance pass, or `gent transport clean` compacts at most eight full records; a large batch or legacy backlog may need multiple passes. Dry-run verifies candidates without changing them.

Schema version 11 admits at most 1,048,576 distinct accepted revisions per endpoint. Each revision needs a 32-byte verification digest, so new admissions bound that payload at 32 MiB, excluding revision keys and SQLite overhead. Legacy full records without a saved digest already count toward the limit. Replacing a verified legacy body with its digest consumes its reserved slot, even when a migrated database is oversized. Migration never deletes accepted evidence, and repeated matching digests remain usable at capacity; conflicting digests still fail.

New revision admission, including bootstrap, reserves capacity before inserting its full history record. A failed batch rolls back all its authority, digest, full-history and projection changes. A receiving stream retains the unaccepted packet without advancing its committed head. Publication of already accepted history and duplicate-stream verification remain available at capacity, including the existing expired-lease configuration recovery path. Ordinary chat permissions and freshness checks still apply.

The cap includes automatic renewals. Reaching it blocks further signed changes and renewal; the current lease can then expire. `gent transport` reports accepted revision usage, the cap and legacy reservations. Cleanup preserves these digests and cannot release revision slots. Do not delete verification evidence to make room. A future authenticated archival or checkpoint-transition design is required to extend an endpoint beyond this lifetime limit; that design is not implemented.

Accepted digests remain trusted endpoint state, like the current authority checkpoint. They do not reconstruct deleted policies or prove them to an independent third party. Standalone replica history has no record-retention policy. All Gent-owned databases have the allocation limit below; transaction journals, temporary files and backups need additional space. Corruption or rollback of the trusted endpoint database remains outside these protections. Compaction has no service-side plaintext effect and supplies no forensic-erasure guarantee.

Nine added tests cover record/byte quotas, rollback, corrupt historical records, bounded dry-run, version-5 migration, joined-node migration pins, partial publication, offline and duplicate streams, delayed messages/configuration results, interrupted pairing across 80 newer revisions, and expired-writer configuration publication without enabling data or revoked readers. The existing lease, revocation, ordering, and retry tests remain in force.

Six additional tests cover accepted-revision capacity, reserved legacy evidence, matching/conflicting retries, atomic batch and bootstrap refusal, duplicate streams at capacity, buffered-revision recovery, expired-history publication and oversized migration with injected compaction failure.


## Database allocation and journals

Every Gent-owned connection to `state.sqlite3`, `mls.sqlite3`, or `authority.sqlite3` sets SQLite's `max_page_count` to a 2 GiB allocation ceiling. This includes table, index and freelist pages; it complements the logical component quotas above. The limit is applied on every open because it is a connection setting. For an existing database larger than 2 GiB, the ceiling is its current page count: accepted state remains intact and existing pages can be reused, but the connection cannot allocate more pages. Gent does not automatically vacuum or discard verification evidence.

Runtime and MLS schema versions 12–13, and standalone replica version 2, use SQLite `journal_mode=DELETE`, `synchronous=EXTRA` and `secure_delete=ON`. Gent serializes runtime access through one connection. Rollback journaling keeps transaction before-images instead of retaining a WAL across commits. SQLite's `journal_size_limit` would not provide a hard WAL limit: a pinned reader can prevent checkpoints indefinitely. With rollback journaling, an external reader can instead delay a commit; Gent waits up to five seconds and then reports failure. Failed transactions roll back, and requests can retry after the reader releases its snapshot. This tradeoff needs latency measurement in the daily-use trial.

SQLite performs the WAL-to-rollback conversion itself. An active connection that prevents the required locks makes opening fail; stop other database users and retry. Gent never deletes a WAL or hot journal to force an upgrade. Committed WAL contents and interrupted rollback transactions recover through SQLite. Unknown future schema versions are refused before changing journal mode, and older Gent binaries refuse the new schema versions.

`gent files` reports allocated and reusable database bytes, the configured and effective page ceilings, and oversized legacy state. A full-database error rolls back enclosing message/authority changes. Tests also compare the complete stored MLS database across a failed send and verify successful retry after releasing fixture capacity. Some OpenMLS storage failures surface as generic internal library errors; their error text does not identify the quota reliably. Cleanup can reuse freed pages, but it still needs disk space for its transaction journal and may require page allocation. Physical filesystem exhaustion or a required migration can therefore prevent cleanup or startup. There is no reserved emergency disk pool.

**The 2 GiB ceiling is per database, not a total directory or filesystem quota.** A transaction journal can retain before-images for much of the database plus record/header overhead. Temporary query files, plaintext handoffs, logs and backups consume additional space. Existing oversized databases retain their larger footprint. External programs running as the trusted OS user can write files or open SQLite with different settings. Tracked handoffs and new export reservations have the admission limits below; aggregate filesystem budgets remain unfinished. Logical deletion and rollback journaling do not establish forensic erasure or protection against restoring an old backup.

Eight added tests cover page-size accounting, database-full rollback and page reuse, oversized legacy state, pinned readers, repeated cache spills, live-WAL conversion refusal, abrupt-process recovery, message request atomicity, and stored encryption state. The native `scripts/smoke_storage.py` proof exercises CLI diagnostics, a blocked MCP send, retry/delivery after releasing a reader, migration of a crash-left version-11 WAL, and exact retry after restart.


## Plaintext handoff admission and export recovery

Schema version 13 limits a node to 4,096 handoff records/reservations and 512 MiB of recorded or reserved plaintext. Imported sources and completed exports share the budget with pending exports. New import admissions roll back their encrypted objects and retry record if tracking cannot reserve capacity. Hosts may already have written an untracked source file; Gent cannot prevent that external write. Identical tracked copies can extend their deadline at capacity. Replacing or editing a file changes its identity stamp and requires a new slot. Old records remain counted until cleanup can retire them. Existing oversized ledgers retain their records and reject new admissions.

An export uses three committed steps. First, after checking current node/chat authority and object access, it reserves one slot and the complete expected plaintext size in `file_exports`. Next it writes a stable, private `.gent-export-<reservation-id>.tmp` file and saves its inode, size, timestamps and expected digest. Finally it publishes with a no-replace rename, records the completed handoff and releases the reservation in one database transaction. Every step rechecks current authority, registration, file permissions and expiry. The reservation binds the object ID, chat, filename, digest, byte length and deadline; a mismatch fails before filesystem work. Consuming an existing reservation transfers its capacity even when the overall ledger is oversized.

A failed reservation creates no new plaintext. A failed write or stamp commit leaves the same reserved temporary path available for retry. An explicitly requested retry may append the remaining bytes only when the temporary file matches a prefix of the currently authorized source. It never truncates or replaces different contents. Once the complete stamp commits, publication verifies that exact temporary file; after an interrupted rename, it accepts only the expected inode and complete digest at the destination. A failure recording the final handoff leaves the committed reservation available for retry or expiry cleanup. This prevents repeated failures from creating a new temporary filename on every call. External edits can still race filesystem operations under the trusted OS user; these checks are not process isolation.

Expiry maintenance and `gent files clean` each process up to eight pending exports in addition to the eight ordinary handoff copies. Verified unchanged temporary/published files can be removed using the existing quarantine mechanism, and missing files release their reservations. Changed, linked, substituted, corrupt or unverified files remain reserved and visible. If a crash happened before the completed stamp committed, cleanup cannot prove ownership of the current file and preserves it. Retry while the source remains accessible, or inspect/remove the copy manually and run cleanup after expiry. A changed quarantine is left at its recovery path when the original name is ambiguous. Failed database deletion can recover on the next pass after the filesystem deletion; ordinary cleanup remains available after loss of cluster membership.

`gent files` reports the combined record/byte budget, pending export reservations, final/temporary/quarantine paths, verification state and cleanup outcomes. Error text is bounded to 1 KiB. Cleanup is bounded and preserves preview semantics. Eight added tests cover independent byte/record quotas, exact retries and completion at capacity or above it, failed reservation/stamp/publication/deletion writes, prefix recovery, changed files, metadata conflicts, per-phase revocation, quarantine recovery, bounded cleanup and version-12 migration. `scripts/smoke_handoffs.py` uses native CLI/MCP processes, a killed daemon and an explicit partial-file fixture to verify retry with the same inode, quota refusal, diagnostics and cleanup. The physical pairing proof injects a failed export-ledger insert on the receiving machine, restarts both daemons, then recovers exact file bytes and forwards them.

These limits cover Gent admissions, not every byte or inode under `~/.gent`. User edits, moved/untracked files, older untracked exports, empty directories, backups and SQLite journals/temporary files need separate operational budgets. A preserved file remains counted at its recorded size, even if an external program enlarges it. Quotas cannot prevent arbitrary writes by the OS user, and cleanup does not guarantee forensic erasure.
