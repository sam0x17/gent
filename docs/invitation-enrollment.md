# Invitation enrollment design

November 15, 2026. The offer, claim, encrypted channel, owner admission journal, daemon polling and joining session driver are implemented. Private-file CLI enrollment connects these components to the account and relay Workers, with durable invocation IDs, independent node credentials and explicit continuation. Physical Linux-Mac enrollment passes in both directions against local Workers, including continuation after actual expiry. Scoped replacement of a lost joined node and SSH joining are also available. The private trial services are deployed.

An invitation admits one trusted daemon to an existing cluster. It must authenticate the owner independently of Gent's service, protect bootstrap metadata and keys, and preserve the same joining identity across interruptions. Initial enrollment requires the same human account on both machines. Hosted agents and future multi-user admission need separate, narrower capabilities.

## Trust and delivery

`gent node add laptop` issues a named invitation from an existing configuration-authorized node. It displays `gent2-CLUSTER.NODE.SECRET`, with percent-encoded labels and a 256-bit random secret. Both labels are bound to the capsule authentication and lookup digest. Legacy `gent1-` codes remain readable. The new machine runs `gent cluster join CODE`. It decrypts the invitation and continues through the existing Noise protocol using the owner-signed name. An authorized joined node requests the offer and activation from the signing owner through authenticated MLS control traffic. The cloud service never handles that private control traffic in plaintext. See [setup commands](service-setup.md#add-another-machine-through-gent).

SHA-256 with separate domain strings derives the lookup ID and encryption key from the random secret. ChaCha20-Poly1305 uses a random 96-bit nonce and authenticates the account, cluster, lookup ID, creation time and direction. The service receives only the ID, account/cluster routing metadata, timestamps and ciphertext. It cannot replace the native trust anchor or assigned name without the private code and a valid owner signature. This is a high-entropy secret transfer, not a short-password protocol. Keep it private. The literal CLI form can be retained by shell history; the prompt and private-file forms avoid putting it in command arguments.

Codes expire after 15 minutes. The service bounds capsule sizes and retains at most eight codes per cluster and 128 globally. Publication permits only identical retries and binds the issuing session, existing node and native invitation. Revocation of any of those authorities closes delivery. Private endpoint journals preserve the same code, ciphertext and joining identity across retries. Expired issuance journals are cleaned before a fresh `node add NAME`. Native admission enforces one joining identity even if multiple machines have downloaded the same ciphertext. A repeated `gent node add NAME` after expiry binds its new offer to the existing member if that name was already enrolled. The joining CLI validates it against the saved identity and owner pins, then resumes automatically. An ambiguous name is rejected. `gent cluster join` without a code resumes the saved attempt; it never resets the node.

The original file interface remains available. The owner creates an invitation through its local owner-authenticated CLI. The interface writes a private file, which the user transfers through an independently trusted channel:

```sh
gent cluster invite --out /private/path/laptop.gent-invite
gent cluster join --invite-file /private/path/laptop.gent-invite --name laptop
gent cluster invitations
gent cluster invitations revoke INVITATION_ID
```

Output contains the invitation ID, path, expiry, privileges and next command, with no secrets. Secrets stay out of command arguments, shell history, model tools, logs, and the ordinary TOML configuration. The joining CLI checks private, regular, nonlinked input and pins the offer in a private journal before exchange or pairing effects. A pasted web page or relay-supplied trust anchor cannot replace this transfer. A URL/QR interface can follow once its endpoint handling is proven; a URL fragment alone does not protect secrets from the page that reads it.

Both machines must already be signed into the same account and service. The owner daemon must be online. New nodes receive configuration-editing authority by default; `--no-configure` limits enrollment to messaging. The private file expires after 15 minutes and must remain private after transfer. The CLI refuses an existing unrelated output file and preserves exact retries of the same output path and options.

`gent cluster invite --replace-node OLD_NODE_UUID --out FILE` authorizes replacement of one lost joined node, binding its exact ID and signing key. It preserves that node's configuration rights by default; `--no-configure` can only reduce them. The joining command uses the ordinary `--invite-file FILE --name NODE` syntax from a fresh directory. Enrollment retires the old ID/key and admits the claimed fresh identity atomically. Issuing or claiming the offer alone does not retire the target. The signing owner is excluded, and ordinary invitations cannot request replacement. See [recovery](recovery.md#replace-through-a-private-invitation) for retry, continuation and migration limits.

The owner keeps creation request IDs, options and issuing-session hashes under `~/.gent/invitations/`. These records contain no invitation secrets; the daemon's private journal supplies the same draft for retries. Creation retains at most 128 records and prunes expired creation requests on subsequent commands. Service registration precedes local activation and output publication. Revocation closes local admission first, then service routing; a failed service acknowledgment reports pending revocation and can be retried. Already-admitted membership requires separate node removal.

The joining CLI stores its signed offer, node binding, scoped bearer, exact invocations and completion receipt in `~/.gent/auth/invitation-join.json`. This location survives staging cleanup and preserves existing account login. It is bounded to 8,192 invocations and 16 MiB. Each UUIDv4 invocation and its complete input are saved before sending; an uncertain invocation is resolved before a different action. Retries use the original issuing login and bearer. Changed account/service/owner/name/privilege pins are refused.

For an interrupted join, rerun the original command. If the invitation expires or is revoked, issue a replacement. When the node is already enrolled, use `gent cluster invite --out NEW_FILE --continue-node NODE_ID`, preserving `--no-configure` if used originally. On the joining machine, pass the new file and `--continue`. The replacement must preserve the pinned owner, service, privileges and saved node; up to 16 superseded offers are remembered to prevent cycling back. If no membership was created, a new-node offer can continue the saved identity. A different login requires a replacement offer rather than silently allocating another bearer for the old offer.

The existing staging engine still publishes `config.toml` last. A post-publication callback runs under the setup and daemon locks, with the committed node key, including on already-joined and interrupted-publication retries. Failure to obtain the encrypted Finish receipt returns `joined: true` with `invitation_receipt_pending` and retry instructions. It does not reset the installed node. Once an offer expires, it cannot return its original receipt; the installed node retains its membership and transport configuration.

An owner-signed offer binds the protocol version, UUIDv7 invitation ID, cluster trust anchor, issuing owner node, account ID, canonical account and relay origins, per-invitation Noise responder public key, intended node privileges, issue time, and expiry. The ID embeds the whole-second issue time; the native verifier requires it to agree with the signed timestamp. The service derives the fixed 15-minute deadline from that ID, so deleting expired rows cannot make an old ID admissible again. The offer also binds the digest of the invitation's routing credential. The owner signs a domain-separated canonical encoding. The recipient trusts the offer's anchor because of the protected transfer; verifying a signature against an anchor supplied by the service is insufficient.

The file includes a fresh, system-generated 256-bit Noise preshared key and an independent routing credential. It never includes the owner's signing key, account session, or normal node transport credential. The owner persists its draft, including the per-invitation responder private key, before registering the invitation with the service. A lost registration response must retry that draft rather than generate a new invitation.

## Separate service and endpoint checks

The routing credential grants temporary access only to the joining side of one invitation mailbox. The service stores its digest, opaque account/cluster/owner-node/invitation IDs, expiry, and transport status. It receives neither the Noise secret nor the signed offer, node display name, private policy, MLS packages, or grants in plaintext. Routing IDs, ciphertext sizes, timing, and account associations remain visible.

The owner CLI registers the mailbox under its account session. The owner daemon accesses the owner side with its existing node credential; it need not hold an account bearer. Service checks bind that credential to the designated owner node and cluster. The joining side requires its own current session for the same account as well as the invitation routing credential. Each side can write only its own direction and read only the corresponding reply direction. A routing credential cannot read normal cluster mailboxes, files, or other invitations.

The account bearer goes only to its previously pinned account origin. The CLI must compare the signed offer against that origin and account before enrollment, and check service ownership as the SSH flow does. Relay requests use scoped credentials. Service authorization is required for storage access, but only the native owner can approve a cryptographic member.

## Service authorization and mailbox routes

The local account Worker registers routing metadata through `PUT /v1/clusters/CLUSTER/invitations/INVITATION`. The body contains `owner_node_id`, the lowercase hexadecimal SHA-256 of the raw 32-byte routing secret, and `expires_at`. The service requires the current cluster owner, an active designated owner node and the UUID-bound deadline. Issuing session, owner node, routing digest and expiry are immutable. Exact retries keep their original record. `DELETE` permanently revokes the record; deletion of an absent, unexpired ID first reserves a tombstone so concurrent registration cannot restore it. An expired ID cannot be registered again after cleanup.

The joining client exchanges the routing secret and a privately saved, client-generated `gent_j1.<creation-seconds>.<64-random-hex-characters>` bearer at `POST /v1/invitations/INVITATION/session`, authenticated under its own account session. The routing secret is encoded as 64 lowercase hex characters. Its digest and the same human account must match the invitation. SQL stores only the joining bearer's digest, its issuing session and scope. The joining bearer is separate from both account and ordinary node credentials and cannot access normal mailboxes, files or notifications.

Owner-side requests use the designated node's normal transport bearer. Join-side requests use the scoped joining bearer. Every relay request checks the account service through its separately authenticated internal binding, including a second check after buffering a write and entering the storage gate. Both sides require the invitation's original owner session, current owner membership, active account/cluster and active designated node. Join-side access also requires its own issuing session. Logout, revocation and expiry deny subsequent checks; restoring account or membership state does not reactivate revoked records. A request already admitted before revocation may finish.

The account API limits each cluster to 128 retained invitation records and 4,096 retained joining credentials, with 64 retained and four active joining credentials per invitation. Cleanup removes up to 64 expired invitation records per registration and cascades to their joining verifiers. Exact retries and revocation of existing records work at capacity. These limits are separate from native cryptographic admission and do not grant node membership.

The service-auth relay adds these opaque binary routes:

| Method and path | Authorization and behavior |
| --- | --- |
| `GET /v1/invitations/INVITATION/attempts` | Designated owner only; bounded map of attempt UUIDs and next sequence numbers for both directions. |
| `PUT /v1/invitations/INVITATION/ATTEMPT/SIDE/INDEX` | Write only the authenticated side (`join` or `owner`). Append the next sequence or retry identical bytes. |
| `GET /v1/invitations/INVITATION/ATTEMPT/SIDE/INDEX` | Read only the other side. Missing messages return 404; reads do not consume them. |

An attempt uses a UUIDv4 and starts with the joining side's sequence zero. The owner cannot create an attempt independently. Each invitation has a dedicated Durable Object, at most 64 attempts, and independent limits of 4,096 messages and 64 MiB of ciphertext in each direction across all attempts. A message is at most 6 MiB plus 4,096 bytes for compact frame packaging. The relay interprets neither Noise messages nor pairing operations. Byte-identical retries preserve existing counters at capacity; changed bytes under an existing sequence fail.

Messages are stored in 64 KiB chunks with their length and digest. Chunks, the message descriptor and ledger counters commit in one storage transaction. A FIFO lock orders complete operations across asynchronous service/storage calls. Expiry alarms remove the object's storage at the UUID-bound deadline; failed cleanup retains an alarm retry. Revocation denies access but does not immediately erase existing ciphertext. Base64 encoding, database metadata and runtime overhead require more storage than the ciphertext quota. Cluster-wide and service-wide usage budgets remain required before trial deployment.

The shared-token development Worker has no invitation routes. Account and relay state remain local prototypes. The native `Mailbox` client takes a separately trusted signed offer and uses its relay origin. Owner clients accept only node transport bearers; joining clients accept only invitation bearers. Neither accepts an account login bearer. The client refuses redirects, bounds response bodies, checks the local deadline before and after network reads, and omits remote bodies and URLs from errors. Only owners can enumerate attempts; message methods write their own direction and read the peer's direction. Listings are untrusted hints, checked against the offer deadline, canonical IDs and service limits.

The HTTP client does not advance Noise counters or regenerate ciphertext. The session drivers retain the original envelope for an uncertain upload and use a fresh attempt after losing session state. Daemon startup and shutdown now manage the owner driver independently of normal configuration/message sync. The joining driver accepts a previously saved node identity and an invocation whose ID/input the caller must preserve across process restarts. The CLI now connects these APIs to private invitation files, account exchange and durable invocation IDs. Service admission alone cannot provide the private trust anchor or approve the joining node.

## Native session drivers

Both mailbox directions use the same sequence for a request and response. Sequence 0 holds the empty Noise handshake. The joining side sends its encrypted signed claim at sequence 1; after durable admission, the owner replies with encrypted `gent/invitation/claimed/v1`. Pairing invocations and their encrypted responses begin at sequence 2. The claim receipt releases no cluster snapshot and is not a completed-enrollment receipt.

The owner caches one outbound envelope per live attempt until the relay confirms storage. It advances the input sequence only after that confirmation. Retrying a lost acknowledgment sends identical ciphertext and does not decrypt the input twice. Before releasing a cached response, the owner rechecks the current local invitation authority. Revocation cannot retract bytes already sent. A new accepted claim for the same saved node/key/name supersedes that invitation's older established sessions, releasing slots left by cancelled callers; an unauthenticated Hello cannot supersede them.

The scheduler retains at most 128 invitation jobs, eight live sessions overall and two per invitation. It rotates through batches of eight jobs with four concurrent network workers. Each attempt retains at most one response within the wire limit; incoming bodies and transient crypto/HTTP copies require additional memory. Sessions normally end after 30 idle seconds and always end at their five-minute channel lifetime. Malformed candidates are skipped in a bounded set of at most 64 IDs per invitation. Admitted IDs remain in the durable journal across restart. Requests back off from 500 ms to ten seconds after failure. With no invitations, the worker checks local state once per second and sends no invitation traffic. Dropping the worker aborts its task; Store work runs in blocking tasks without holding its mutex across HTTP awaits. Credential-file changes replace the mailbox bearer while preserving live session state.

The joining driver uses a fresh session after cancellation, failed authentication, lost session state or an idle period of 20 seconds. Each exchange normally waits at most 30 seconds, retrying the original upload bytes before polling its matching response. One invocation permits at most three session attempts; it preserves the invocation ID and input through those attempts. Authentication, authorization and sequence refusals terminate immediately; network/server errors can retry within the deadline. A normal authenticated owner error is returned to the caller without opening another session. Handshake reads are limited to 57 bytes and claim/receipt reads to their smaller protocol bounds. Ordinary encrypted operations retain the 6 MiB pairing limit.

HTTP 429 is temporary. Invitation mailboxes honor `Retry-After` on 429 and on 503 responses that include it. Delta seconds and HTTP dates become monotonic cooldowns, bounded to 1-120 seconds; missing, malformed or duplicate values use five seconds. Cloned mailboxes share separate data and attempt-listing cooldowns. Calls made during a cooldown return a local temporary error without another HTTP request. Bodies, URLs, credentials and reflected header values are absent from those errors. Other relay clients retain their existing retry schedules.

A joining exchange preserves its exact ciphertext, attempt ID and known upload acknowledgment through these pauses. The pauses may add at most 120 seconds to that exchange's ordinary wait; repeated hints cannot extend it indefinitely. If the hint cannot fit, the call returns a temporary error and retains the durable enrollment operation for an explicit retry. Owner sessions retain their cached responses and get an idle grace period through the advertised pause, but the five-minute Noise session lifetime, signed invitation deadline, revocation and local clock checks still apply. Restart and cancellation keep the existing fresh-session recovery rules; cooldowns themselves are memory-only.

## Encrypted channel component

The `gent-crypto` crate's optional `invitation` feature implements the established [Noise protocol](https://noiseprotocol.org/noise.html), using `Noise_NKpsk0_25519_ChaChaPoly_SHA256`. The native daemon enables this feature; the relay Worker does not. The joining endpoint knows the responder public key from the protected offer; both endpoints know the independent preshared key. Each connection attempt uses fresh ephemeral keys. The handshake prologue binds the complete signed offer and a fresh UUIDv4 attempt ID, preventing cross-invitation, cross-service, or protocol substitution.

Both handshake payloads are empty. No node identity, snapshot, grant, or enrollment operation travels as early data. After the handshake, the initiator sends an encrypted, node-signed claim before the responder releases cluster metadata. This gives the responder confirmation of the completed channel and binds the new identity to that attempt. Record secrecy after later compromise of long-lived invitation material depends on fresh ephemeral keys and disposal of session secrets; it does not cover compromise of a running endpoint or retained secret-memory copies.

[Snow 0.10.0](https://docs.rs/snow/0.10.0/snow/) supplies the protocol state machine, SHA-256 and ChaChaPoly implementation. Thin resolver adapters use the workspace's system RNG and `x25519-dalek` 3 with contributory-DH checks and its zeroizing secret types. Snow requires its Curve25519 feature for the default hash/cipher resolver to compile, but Gent's resolver overrides DH. A published Cacophony vector checks the exact handshake ciphertexts, final hash and both transport directions; the fixture includes its provenance and license notices. Tests also reject low-order and zero-equivalent public points.

Invitation secrets, private-file encodings and decrypted messages use zeroizing buffers, and secret/channel types have no `Debug` or automatic serialization. Session counters and keys have no persistence API. Snow's cipher and handshake internals still contain raw key material without comprehensive zeroization; this component makes no claim that all secret-memory copies are erased. Endpoint-memory hardening and independent protocol review remain required before production use.

Noise messages are at most 65,535 bytes, while the current pairing frame limit is 6 MiB. Each encrypted fragment contains a one-byte version (`1`), a four-byte total plaintext length and four-byte offset, both big-endian, followed by at most 65,510 data bytes. A message uses exactly the required number of fragments, up to 97; even an empty message uses one authenticated fragment. The receiver checks ciphertext bounds before decryption, checks the authenticated total before allocating the message, and returns bytes only after every fragment passes. Truncation, reordering, substitution, reflection, and malformed framing close the channel without exposing a partial operation.

Each direction admits at most 4,096 messages and 64 MiB of plaintext, including the claim. A session expires after five minutes or at the offer deadline, whichever comes first. Trusted-clock rollback, expired sessions, exceeded budgets and cryptographic errors close the channel. A closed channel cannot be reopened by correcting the clock or resubmitting a packet.

Session keys and counters stay in memory. A process restart or uncertain session starts a fresh handshake; it never reconstructs an old session with reset counters. The transport can resend cached, byte-identical ciphertext within a live attempt, with exact duplicate handling outside Noise. Application retries across attempts use durable operation IDs and input digests. Authentication errors terminate the attempt; they do not fall back to plaintext or a development token.

## Single-use admission and restricted operations

The first encrypted request is a node-signed claim over the offer digest, invitation ID, completed handshake hash, node ID/public key, chosen name, and bounded validity period. The joining identity is generated and saved locally before this request. It cannot select owner authority or additional privileges.

The owner verifies the claim and atomically binds an unclaimed invitation to that node ID, key, and name before returning a snapshot or enrolling anything. A second claimant loses even if its cryptographic handshake succeeds. A reconnecting claimant must prove possession of the same node key in its new channel. SQL approval at the service cannot create, replace, or clear this native binding.

The library implements claim verification and requires an admission callback before exposing a response-capable owner channel. Claims last at most 60 seconds and cannot outlive their offer. Callback failure destroys the pending session. The native daemon's callback now persists the claim before releasing that channel. A private persistent lock serializes invitation operations across Store instances and processes; revocation also takes this lock. Tests race separate Store instances and reconnect after restart with matching and competing identities.

The current `Store::pair` API assumes owner authentication. Invitation holders instead use `Store::invitation_call`, which accepts authenticated Noise frames and enforces the following scope before invoking the shared pairing implementation:

| Operation | Required restriction |
| --- | --- |
| Snapshot | An accepted claim for this invitation and cluster; service metadata only, without the owner's transport credential. |
| Enroll | The exact claimed node/key/name, signed request, offered anchor, replacement scope, fresh checkpoint and current owner-approved privileges. Existing membership still requires proof of the same key. |
| Configuration | The claimed peer and its verified MLS credential; durable request/input binding and recorded resulting group. |
| History | This cluster and the retained bootstrap checkpoint/history needed by this join, with bounded reads. |
| Data | The claimed peer, verified key package, and request/group bindings; no legacy-agent migration through a new-node invitation. |
| AcceptData | The claimed signer and roster, and the exact outgoing group created for this invitation. |
| Finish | The claimed node and completed bootstrap; an idempotent completion receipt. |

No other owner RPC is reachable through this dispatcher. Ordinary SSH joins grant configuration-editing authority; invitation privileges are explicitly bound in the offer and enforced when choosing the enrollment operation. An invitation grants no ability to mint another invitation or enroll a different node. Each operation rechecks the current signed membership, issuing owner, service binding, saved claim, privileges and retirements.

Native state progresses from draft to issued to claimed to complete. Revoked and expired records are terminal. Claiming permanently consumes the right to select a node; a claimed invitation may finish that same node before expiry. Completion permits only its bounded receipt retry, not further pairing operations. Each mutation checks current authority, native invitation state, and expiry. Revocation serializes with admission; it cannot undo an already committed membership or retract keys already delivered. Removing an admitted node requires the separate cryptographic and service revocation flow.

The dispatcher persists each operation ID and canonical input digest before side effects. Existing pairing operations span more than one transaction, so the journal alone does not make them atomic. Retries recover committed cryptographic operations, then save completion and group bindings before replying. Snapshot and history retries read current authorized state; the journal does not cache stale plaintext responses. Fault-injection tests cover committed enrollment, configuration/data grants and a data link followed by a failed journal write.

Configuration and data requests have a cryptographic request namespace bound to the cluster, claimed node ID/key, operation kind and original request UUID. It is deliberately independent of the invitation ID, so explicit continuation can recover an existing group. A new invitation still records its own successful Data result before accepting the return stream.

## Native journal and limits

Database version 14 adds invitation records, operation reservations and an admission clock. Migration preserves existing keys and state. Opening an established version-14 database refuses missing invitation tables or the clock row. Draft creation uses UUIDv7 request IDs with a 15-minute first-admission window; exact retries preserve the original offer and secrets, while changed options fail. Owner activation is a separate local operation. The CLI registers the service record before requesting activation.

Database version 15 adds durable admitted-attempt IDs. After authenticating a Hello, the owner commits its attempt ID and budget increment together before releasing the handshake response. A previously admitted ID cannot start another session, even with different Hello bytes, after a failed delivery or after restart. Live transport retries must reuse the cached response; lost sessions require fresh IDs and handshakes. Expiry cleanup also removes attempt rows. An established version-15 database refuses a missing attempt table. Upgrading closes any version-14 offer that already admitted a handshake, because its old attempt IDs were not retained; keys and enrolled membership remain intact. Unused offers remain available, and partial enrolled nodes can use explicit continuation offers.

The journal retains at most 128 invitations, including revoked records until their original expiry. Each invitation permits 64 authenticated handshake starts and 8,192 operations; the node-wide operation limit is 32,768. Configuration, Data and AcceptData each permit four operation IDs per invitation. Existing exact retries remain available at capacity. Invalid PSK handshakes do not consume the authenticated-attempt budget. Native operation limits and service request/byte quotas are independent.

Revocation removes the private invitation secret and operation rows. Completion retains the secret until expiry so a fresh session from the same node can retrieve the original successful Finish receipt. Newly allocated or previously failed Finish IDs cannot become successful after completion. Other pairing operations are closed. Startup/periodic maintenance and invitation entry points delete expired records and their operation and attempt rows. SQLite deletion makes no forensic-erasure guarantee for database pages, WAL files or backups.

## Expiry and recovery

Offers have a fixed 15-minute lifetime. Retries cannot extend it, and each endpoint uses its trusted local clock rather than a time supplied by the relay. The owner persists an admission-time watermark separately from operation transactions. Even failed cleanup commits the observed time, so ordinary clock rollback cannot reopen an expired invitation. The creation-ID admission window prevents recreating the original invitation after cleanup. Service cleanup must preserve its corresponding rule that an old ID/credential cannot be admitted again after its verifier is removed. Whole-endpoint backup rollback remains part of the separate recovery design.

An expired partial join retains its node key and staged state. A replacement invitation can explicitly authorize continuation of an already enrolled node with that exact key, name and privileges. It cannot revive a retired node. Native tests revoke interrupted invitations, issue explicit continuations and finish the staged join with the original node key and groups. An expired invitation that never enrolled the node can be replaced with a new-node offer while retaining the local staged identity. Private-file joins expose these flows through explicit replacement with `--continue`. Named code joins select continuation automatically while preserving the same pins. Named continuation offers also retain the inviting node, so its revocation or loss of configuration rights closes the offer. Once the existing publication manifest is committed, local publication can finish without fresh owner pairing operations; normal account/transport checks still apply.

For a lost-node replacement, a fresh offer before enrollment must retain the same `replaces` target. After enrollment, `--continue-node NEW_NODE_UUID` derives that scope from the durable retirement mapping. The joining journal requires equality of the old and new offers' scope; an ordinary offer cannot downgrade a replacement join. Current membership, target keys, privilege limits and the mapping are checked again before each native operation. Revoking an invitation after retirement committed cannot revive the old node.

Preserve the current joining locks, account directory, service pin, immutable publication manifest, and `config.toml`-last installation. Provision the joined node's own transport credential under its account session. Failure cannot copy the owner's credential or publish a newly generated identity over partial state.

Service revocation stops transport; native revocation stops further cryptographic admission. Either check can deny a join. The service can withhold or reorder traffic, and an unavailable owner cannot finish enrollment. Completed nodes use their established encrypted streams independently of the invitation mailbox. Removing invitation secrets and ciphertext is cleanup, without a forensic-erasure guarantee.

## Wire records and remaining acceptance work

Offers and claims use RFC 8785 canonical JSON and domain-separated Ed25519 signatures. Unknown fields and noncanonical encodings are rejected. A signed offer permits up to 8 KiB plus the bounded 128 KiB [owner succession chain](owner-succession.md); private joining/owner file encodings permit 16 KiB plus that chain and use distinct structures. Epoch-zero records omit the chain and preserve their existing canonical format. The joining file contains the signed offer, PSK and routing secret. The owner record additionally contains the Noise responder private key. Decoding verifies the owner signature, responder-key shape and routing-secret SHA-256 binding; protected delivery supplies provenance, and the handshake verifies the PSK. Admission separately requires the current owner epoch and issuer authority. The owner record also checks the private/public responder-key match. Private-file parse errors do not echo their input.

Offer IDs are UUIDv7; handshake attempt IDs remain UUIDv4. Earlier component-only UUIDv4 offers are rejected. The private trial now deploys this invitation service; no earlier UUIDv4 offer format was released.

The prologue is `gent/invitation-channel/v1\0` followed by canonical JSON for `[signed_offer, attempt_id]`. Offer signing uses `gent/invitation-offer/v1\0` followed by the offer body; the claim's offer fingerprint hashes that same domain followed by the complete signed offer. Claim signing uses `gent/invitation-claim/v1\0`. The claim contains the invitation ID, offer fingerprint, completed Noise handshake hash, node ID/key/name and validity period. Neither handshake message may carry an application payload; each is exactly 48 bytes.

Native envelopes start with the eight bytes `GENTINV\x01` and a one-byte kind. Kind 0 carries exactly the 48 handshake bytes, making a 57-byte envelope. Kind 1 carries a big-endian u16 fragment count, then a big-endian u16 length and ciphertext for each fragment. Counts are 1–97, fragment lengths are 25–65,535 bytes, trailing bytes are forbidden, and total size cannot exceed the service wire limit. A maximum 6 MiB plaintext message fits with its authenticated fragment headers, tags and envelope overhead. The attempt ID comes from the mailbox path and remains bound by the Noise prologue. Envelope shape checks do not authenticate its contents; the channel must still authenticate every fragment. The service treats envelopes as opaque bytes.

The library and CLI can issue an offer for a new node or for continuation of an existing enrolled node. Continuation pins the existing ID/key/name and preserves its configuration privileges; it cannot revive a retired node. The native journal enforces this binding on claims and operations. CLI continuation after revocation is exercised through the local Workers with the original key and streams. The physical-machine proof also passes explicit continuation after the original offers reach their actual 15-minute deadline.

This proves enrollment across two machines, not a deployed service or a network path independent of SSH.

Native tests cover envelope boundaries and maximum encrypted messages, HTTP direction and credential restrictions, lost-upload retries, redirects, bounded and malformed replies/listings, durable attempt exclusion, competing Store instances, transaction failure, expiry cleanup and migration. Driver tests add lost acknowledgments in both directions, owner restart after committed enrollment, cancelled joining futures, corrupted ciphertext, complete staged pairing/Finish, global/per-invitation capacity, idle slot release, revocation and malformed first-entry recovery. These use loopback HTTP fixtures with synthetic account provisioning. An opt-in native test exercises the real account and relay Worker APIs and recovers the original Finish receipt after owner restart; its GitHub account is still a fixture.

The separate CLI proof loses account responses after registration, exchange, transport provisioning and revocation commits. It verifies stable invocation IDs and keys, one scoped joining credential, independent node credentials, no duplicate streams through explicit continuation, and retained configuration restrictions. A reconstructed lost local receipt write followed by owner restart recovers the exact original Finish response. The proof scans local Worker/D1/DO captures for tested private values, with positive controls. The separate physical proof exchanges actual PNGs and 2 MiB native files in both directions, exercises ordered relay turns, preserves a queued configuration edit through owner downtime and joined-node restart, and rejects configuration edits from restricted members after continuation. Initial and final scans include local D1, Durable Object storage, R2 files and Worker logs. Neither these selected-value scans nor the integration proofs establish production security, hosted/mobile E2EE, or account/owner recovery.
